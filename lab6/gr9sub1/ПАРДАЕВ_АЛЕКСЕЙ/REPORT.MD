## 2. Теоретическая часть

### 2.1. VFS в Linux

VFS (Virtual File System) --- абстрактный слой ядра, обеспечивающий
единый интерфейс для всех файловых систем.

### Основные структуры:

-   **superblock** --- информация о файловой системе\
-   **inode** --- метаданные файла\
-   **dentry** --- связь имени файла с inode\
-   **file** --- описание открытого файла

### 2.2. FUSE

FUSE позволяет выполнять файловую систему в userspace.

**Поток вызовов:**

    Приложение → VFS → FUSE kernel module → /dev/fuse → libfuse → наша программа

Преимущества: простота разработки, безопасность.\
Недостатки: накладные расходы, более медленная работа.

## 5. Ответы на контрольные вопросы

1. Что такое VFS (Virtual File System) и зачем она нужна? \
VFS — слой абстракции в ядре, который предоставляет единый API для всех типов файловых систем. Благодаря ему приложения обращаются к файлам через стандартные системные вызовы (open, read, write, stat), а VFS перенаправляет эти вызовы к конкретной реализации (ext4, btrfs, NFS, FUSE и т.д.).
Это позволяет: (1) подменять/монтировать разные ФС без изменения приложений; (2) централизованно реализовать кеширование и разрешения; (3) унифицировать работу с именами, inode и т.д.
2. Объясните разницу между inode, dentry и file descriptor. \
inode — объект, хранящий метаданные файла и указатели на данные (размер, права, timestamps, блоки). dentry (directory entry) — запись в дереве имен, связывающая имя файла в каталоге с inode; используется при разборе путей и для кэширования имен. file descriptor — дескриптор конкретного открытого файла в пользовательском процессе: содержит позицию чтения/записи, флаги, указатель на file структуру.
Итог: inode — про файл на диске, dentry — про имя/путь, fd — про открытый доступ процесса.
3. Что хранится в структуре `struct inode`? \
В inode обычно: права доступа (mode), UID/GID владельца, размер файла, количества ссылок (nlink), временные метки (mtime/atime/ctime), указатели на блоки (прямые/косвенные), тип файла, флаги и служебные поля (кеши, счетчики).
Эти данные дают ОС всё, что нужно, чтобы прочитать/адресовать содержимое файла и контролировать доступ к нему.
4. Что такое superblock и какую информацию он содержит? \
Superblock — мета-информация о самой файловой системе: размер тома, размер блока, состояние, счётчик свободных блоков, метки и версии ФС, параметры монтирования и UUID.
Superblock нужен ядру для управления всей ФС: проверок, восстановления, распределения блоков и т.д.
5. Как работает кеш dentry и зачем он нужен? \
Dentry cache (dcache) хранит результат разрешения путей — ассоциацию путь/имя → inode (через dentry). При повторном вызове open("/a/b/c") VFS может пройти по dcache быстрее, не обращаясь к диску.
Польза: уменьшение числа обращений к диску, ускорение операций с файлами и директориями; минус — нужно инвалидация при изменениях (rename/unlink).

### FUSE
6. Как FUSE взаимодействует с ядром Linux? \
FUSE использует kernel-модуль (fuse.ko), который регистрирует файловую систему в VFS и создаёт интерфейс через /dev/fuse. Когда VFS получает запрос для монтированной FUSE-FS, он посылает его в kernel-модуль, который передаёт запросы в userspace через /dev/fuse/libfuse. Пользовательская программа (libfuse) обрабатывает запрос и возвращает результат обратно в ядро.
Таким образом протокол и dev являются мостом для IPC между kernel и userspace.
7. Опишите путь системного вызова `read()` в FUSE FS. \
Приложение вызывает read(fd, ...) → syscall попадает в ядро → VFS определяет, что fd принадлежит FUSE-монту → kernel-formatted request записывается в /dev/fuse → libfuse (пользовательский процесс) читает запрос, вызывает соответствующий callback read() в вашей программе → ваша функция читает/формирует данные и возвращает их через libfuse в /dev/fuse → ядро получает ответ и возвращает данные приложению.
Ключевые моменты: context switch kernel↔userspace и дополнительные копирования буферов.
8. Почему FUSE работает медленнее нативных kernel FS? \
Основные причины: дополнительные контекстные переключения (kernel→userspace→kernel), копирование данных между пространствами, задержки IPC и синхронизации, а также overhead в обработке многих мелких операций. Kernel FS работают внутри ядра и избегают этих переключений.
На практике это особенно заметно при множестве мелких операций (создание/удаление многих файлов).
9. Какие преимущества дает разработка FS в userspace? \
Безопасность (ошибки не крашат ядро), удобство разработки и отладки (обычные отладчики, стандартные библиотеки), переносимость и быстрая итерация. Можно использовать любые userspace-библиотеки (сеть, сжатие, криптография) без kernel-патчей.
Это идеально для прототипов, сетевых файловых систем и специальных трансформаций данных (шифрование, архивы и т.п.).
10. Приведите примеры популярных FUSE файловых систем (sshfs, GCS FUSE, etc.). \
SSHFS (монтирование удалённой файловой системы по SSH), GCS FUSE (Google Cloud Storage), s3fs (Amazon S3), NTFS-3G (NTFS в userspace), fuse-zip/tarfs (просмотр архивов), rclone mount, encfs (шифрование).
Каждая решает свою задачу: сетевой доступ, облачные объекты, шифрование или виртуализация архивов.

### File operations
11. Что делает операция `getattr()` и когда она вызывается? \
getattr() заполняет структуру stat для заданного пути: тип файла, права, размер, временные метки, число ссылок и т.д. Вызывается при stat(), ls -l, перед открытием файла и часто в ходе операций, требующих проверки метаданных.
Это одна из наиболее частых операций — её реализация должна быть эффективной.
12. В чем разница между `open()` и `create()`? \
open() — открыть существующий файл с заданными флагами; create() — создать новый файл (эквивалент open(..., O_CREAT | O_EXCL)), обычно возвращает дескриптор уже открытого файла.
В FUSE эти операции могут вызываться отдельно: при open вы ожидаете, что файл существует; при create нужно фактически создать ресурс на бекенде и вернуть handle.
13. Почему `read()` принимает параметр `offset`? \
Чтобы поддерживать случайный доступ (pread semantics) и параллельные чтения: read() может быть вызвано с произвольным смещением без изменения внутренней позиции файла. Это упрощает реализацию в многопоточной среде и позволяет реализовывать кеширование/частичное чтение.
Также это нужно для корректной работы mmap/async IO и последовательных операций без reliance на per-fd позицию.
14. Как `readdir()` возвращает список файлов? \
В FUSE readdir() вызывается с буфером и callback-функцией filler. Реализация перечисляет имена и вызывает filler(buf, name, &stat, off) для каждого элемента. Это потоковый API: можно выдавать записи по одной, без построения полного списка в памяти.
Важно корректно возвращать . и .. и поддерживать offset для больших директорий.
15. Что должна возвращать `getattr()` для директории? \
Тип — S_IFDIR | права (обычно rwxr-xr-x или заданные режимы), st_nlink (как минимум 2), корректный st_size (для директорий часто не используется), временные метки и владельца. Должны быть заданы права на исполнение/чтение для доступа к содержимому.
Неправильные атрибуты приводят к ошибкам ls/stat и проблемам с доступом.

### Метаданные и атрибуты
16. Что такое атрибуты файла? Приведите примеры. \
Атрибуты — свойства файла, отражаемые в stat: размер (st_size), права (st_mode), UID/GID владельца, количество ссылок (st_nlink), временные метки (atime, mtime, ctime), тип файла и дополнительные флаги (immutable, append-only).
Атрибуты используются для контроля доступа, отображения и поведения ФС.
17. Что означают биты прав доступа (rwxrwxrwx)? \
Девять бит: первая тройка — права владельца (rwx), вторая — группа, третья — остальные. r — чтение (list/read), w — запись (modify/rename), x — выполнение/вход в директорию.
Эти биты комбинируются с UID/GID и масками ACL/umask для решения, разрешён ли доступ.
18. Объясните разницу между mtime, atime и ctime. \
atime — время последнего доступа (чтение); mtime — время последней модификации содержимого файла; ctime — время последнего изменения метаданных inode (права, ссылки, владельцы) или содержимого.
ctime изменяется и при chown/chmod, mtime — только при изменении содержимого.
19. Что такое hard link и как он отличается от symbolic link? \
Hard link — дополнительное имя, указывающее на тот же inode; все ссылки равноправны, удаление одного имени не удаляет данные пока есть другие ссылки. Symbolic link — отдельный файл, содержащий путь к другому файлу; может указывать на несуществующий путь и пересекает файловые системы.
Hard link нельзя создать для директорий (обычно) и не работает между разными ФС.
20. Как FS определяет размер файла? \
Размер хранится в st_size в inode — обновляется при операциях записи/truncate. Для некоторых виртуальных или сжатых ФС st_size может отражать логический размер (распакованный) или фактическое сжатое представление.
При чтении/write FS использует st_size и блоки/указатели, чтобы служить данными.

### Физическая организация
21. Что такое блок в файловой системе? \
Блок — минимальная единица хранения на уровне ФС (обычно 1KiB, 4KiB и т.д.). ФС адресует данные блоками; файл занимает целое число блоков.
Блоки позволяют управлять аллокацией и I/O эффективнее, чем по-байтово.
22. Объясните принцип непрерывного размещения файлов (contiguous allocation). \
Файлу выделяется последовательный диапазон блоков на диске. Плюс: простота и хорошая производительность последовательного чтения. Минус: фрагментация и сложность расширения файла.
Использовался в ранних ФС и в некоторых встраиваемых системах.
23. Как работает организация через связанный список блоков (linked allocation)? \
Каждый блок содержит указатель на следующий блок. Упростает динамическое расширение файла, нет внешней фрагментации, но плоха при случайном доступе (нужно последовательное чтение цепочки).
Пример: FAT — таблица размещения, где блоки связаны через таблицу.
24. Что такое индексный узел (inode-based allocation)? \
Inode хранит массив указателей на блоки: прямые, косвенные, двойные косвенные и т.д. Это обеспечивает быстрый доступ к началу файла и масштабирование для больших файлов. ext-семейство использует такую модель.
Баланс между эффективностью случайного доступа и возможностью больших размеров файлов.
25. Сравните ext4 и btrfs по структуре хранения данных. \
Ext4 — традиционная journaling ФС с inode-ориентированной структурой, extent-алокацией (улучшение над блоками), хорошая простота и устойчивость; ориентирована на производительность и предсказуемость.
Btrfs — copy-on-write (COW), богатая функциональность (снимки, сжатие, дедупликация, встроенная RAID-поддержка), использует B-tree для метаданных и данных; лучше для функциональности и управления, но сложнее и чувствительнее к ошибкам/конфигурации.
Итог: ext4 — стабильность и скорость; btrfs — гибкость и расширенные возможности.

### Производительность и оптимизация
26. Почему большие файлы читаются быстрее, чем много мелких? \
Потому что последовательное чтение больших блоков лучше использует диск/канал, снижает накладные расходы на системные вызовы, переключения и seeks. Много мелких файлов порождает overhead на открытие/закрытие, stat, чтение метаданных и частые seeks.
На SSD часть эффект исчезает, но всё равно метаданные и syscall-overhead сохраняются.
27. Что такое read-ahead и как он улучшает производительность? \
Read-ahead — предвыборка следующих блоков файла в page cache при последовательном чтении. Если приложение читает последовательно, предзагрузка снижает ожидание I/O и повышает throughput.
Настройки read-ahead (количество блоков) и адаптивный алгоритм сильно влияют на эффективность.
28. Как page cache ускоряет доступ к файлам? \
Page cache хранит недавно/часто используемые страницы файлов в оперативной памяти, позволяя избежать дорогостоящих обращений к диску. При повторных чтениях данные возвращаются из RAM, что уменьшает latency и увеличивает throughput.
Также page cache агрегирует записи (write-back), уменьшая количество I/O операций.
29. Почему запись на SSD быстрее, чем на HDD? \
SSD не имеет механических частей — нет перемещения головки и вращения диска, поэтому доступ практически равномерный и с низкой задержкой. SSD обеспечивает высокую случайную IOPS и низкие latency; HDD хорош при последовательных больших транзакциях, хуже при случайных мелких.
Ограничения SSD — wear-leveling, ограниченное число циклов перезаписи и особенности записи (erase-before-write).
30. Какие параметры влияют на производительность FUSE FS? \
Ключевые: контекстные переключения (kernel↔userspace), размер и частота операций I/O, политика и размер буферов/страниц, реализация caching в userspace, использование multithreading в демоне FUSE, опции mount (-o direct_io, -o big_writes, -o allow_other), overhead сериализации запросов и сетевая задержка (для сетевых бэкендов).
Оптимизация: уменьшать число мелких вызовов, использовать batching, настраивать read-ahead, позволять big_writes, использовать эффективные буферы и кеширование на стороне userspace.
