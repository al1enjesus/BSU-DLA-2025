## 2. Теоретическая часть

### 2.1 Архитектура VFS и роль FUSE

**VFS (Virtual File System)** — это уровень абстракции в ядре Linux, который предоставляет единый интерфейс для работы с различными файловыми системами. VFS позволяет приложениям работать с файлами единообразно, независимо от типа физической ФС (ext4, btrfs, NTFS и т.д.).

**FUSE (Filesystem in Userspace)** — это технология, позволяющая реализовывать файловые системы в пространстве пользователя без необходимости написания кода ядра. FUSE состоит из:
- Модуля ядра (fuse.ko) — обрабатывает системные вызовы
- Библиотеки libfuse — предоставляет API для разработки
- Пользовательского процесса — реализует логику файловой системы

### 2.2 Схема взаимодействия

```
┌─────────────────┐
│  Приложение     │  (например: cat, ls, cp)
│   (userspace)   │
└────────┬────────┘
         │ системные вызовы (open, read, write)
         ▼
┌─────────────────┐
│      VFS        │  (виртуальная файловая система)
│   (kernel)      │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  FUSE kernel    │  (модуль fuse.ko)
│   module        │
└────────┬────────┘
         │ /dev/fuse
         │ context switch
         ▼
┌─────────────────┐
│  FUSE daemon    │  (наша программа)
│   (userspace)   │  → обработка операций
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Backend FS     │  (реальная ФС, архив и т.д.)
│  или данные     │
└─────────────────┘
```

**Поток вызова read():**
1. Приложение вызывает `read(fd, buf, size)`
2. VFS перенаправляет вызов в FUSE kernel module
3. FUSE kernel пересылает запрос в userspace через /dev/fuse
4. FUSE daemon обрабатывает запрос (вызывается наша функция `myfs_read()`)
5. Данные возвращаются через FUSE kernel обратно в VFS
6. VFS возвращает данные приложению

| Операция | Описание | Использование |

### Задание A: Passthrough FUSE Filesystem

#### 3.1 Описание реализации

Passthrough FS — это "прозрачная" файловая система, которая проксирует все операции в базовую директорию с логированием каждого действия.

**Ключевые особенности:**
- Все операции перенаправляются в исходную директорию через системные вызовы
- Каждая операция логируется в stderr с временной меткой
- Используется `realpath()` для получения абсолютного пути базовой директории
- Полный путь формируется конкатенацией base_path + относительный путь

**Основные функции:**

```c
// Построение полного пути
static void get_full_path(char *full_path, const char *path) {
    strcpy(full_path, base_path);
    strncat(full_path, path, PATH_MAX - strlen(base_path) - 1);
}

// Логирование с временной меткой
static void log_operation(const char *op, const char *path, int result) {
    time_t now = time(NULL);
    struct tm *t = localtime(&now);
    char timestamp[64];
    strftime(timestamp, sizeof(timestamp), "%Y-%m-%d %H:%M:%S", t);
    fprintf(stderr, "[%s] %s: %s (result: %d)\n", timestamp, op, path, result);
}
```

#### 3.7 Описание реализации

Monitoring FS — это passthrough FS с подсчётом статистики всех операций.

**Ключевые особенности:**
- Счётчики операций и байтов хранятся в глобальной структуре `stats_t`
- Используется `pthread_mutex` для потокобезопасности
- Виртуальный файл `/.stats` предоставляет текущую статистику
- Статистика обновляется в реальном времени

**Структура статистики:**

```c
typedef struct {
    unsigned long reads, writes, opens;
    unsigned long getattrs, readdirs;
    unsigned long creates, unlinks;
    unsigned long mkdirs, rmdirs;
    unsigned long long bytes_read;
    unsigned long long bytes_written;
    pthread_mutex_t lock;
} stats_t;
```

**Обновление статистики:**

```c
static void update_stats(const char *op, ssize_t bytes) {
    pthread_mutex_lock(&stats.lock);
    
    if (strcmp(op, "read") == 0) {
        stats.reads++;
        if (bytes > 0) stats.bytes_read += bytes;
    }
    // ... остальные операции
    
    pthread_mutex_unlock(&stats.lock);
}
```

## 5. Ответы на контрольные вопросы

### Архитектура файловых систем

**1. Что такое VFS (Virtual File System) и зачем она нужна?**

VFS — это уровень абстракции в ядре Linux, предоставляющий единый интерфейс для работы с различными типами файловых систем (ext4, NTFS, NFS, FUSE и др.). VFS позволяет приложениям использовать одни и те же системные вызовы (`open`, `read`, `write`) независимо от типа ФС. Без VFS каждое приложение должно было бы знать специфику каждой ФС.

**2. Объясните разницу между inode, dentry и file descriptor.**

- **inode** — структура данных, хранящая метаданные файла (размер, права, время модификации, указатели на блоки данных). Каждому файлу соответствует уникальный inode.
- **dentry** (directory entry) — кеш-запись, связывающая имя файла с его inode. Ускоряет разрешение путей (`/home/user/file.txt` → inode).
- **file descriptor** — целочисленный идентификатор открытого файла в процессе. Указывает на запись в таблице открытых файлов, которая, в свою очередь, ссылается на inode.

**3. Что хранится в структуре struct inode?**

- Тип файла (обычный файл, директория, символическая ссылка)
- Права доступа (owner, group, others)
- Владелец (UID, GID)
- Размер файла
- Временные метки (atime, mtime, ctime)
- Количество hard links
- Указатели на блоки данных (прямые, косвенные)
- Операции файловой системы (file_operations)

**4. Что такое superblock и какую информацию он содержит?**

Superblock — это метаданные файловой системы, хранящиеся в начале раздела. Содержит:
- Размер файловой системы
- Размер блока
- Количество свободных блоков и inode
- Magic number (идентификатор типа ФС)
- Флаги монтирования (read-only, dirty)
- Указатель на корневой inode

**5. Как работает кеш dentry и зачем он нужен?**

Dentry cache (dcache) хранит соответствие "путь → inode" в оперативной памяти. При обращении к `/home/user/file.txt` ядро сначала проверяет dcache. Если запись найдена, дисковые операции не нужны. Это ускоряет разрешение путей в сотни раз, особенно для часто используемых файлов.

### FUSE

**6. Как FUSE взаимодействует с ядром Linux?**

FUSE использует модуль ядра `fuse.ko` и устройство `/dev/fuse`. Взаимодействие происходит через:
1. Приложение делает системный вызов (например, `read()`)
2. VFS перенаправляет его в FUSE kernel module
3. FUSE kernel записывает запрос в очередь `/dev/fuse`
4. FUSE daemon читает запрос из `/dev/fuse`
5. FUSE daemon обрабатывает запрос и пишет ответ в `/dev/fuse`
6. FUSE kernel возвращает результат через VFS приложению

**7. Опишите путь системного вызова read() в FUSE FS.**

```
1. Приложение: read(fd, buf, 4096)
2. glibc: системный вызов sys_read()
3. VFS: vfs_read() → находит file_operations
4. FUSE kernel: fuse_file_read() → формирует FUSE_READ request
5. /dev/fuse: запрос передается в userspace через device
6. libfuse: fuse_session_receive_buf() читает запрос
7. FUSE daemon: вызывается наша функция myfs_read()
8. FUSE daemon: возвращает данные через fuse_reply_buf()
9. /dev/fuse: ответ передается обратно в kernel
10. FUSE kernel: копирует данные в пользовательский буфер
11. VFS: возвращает количество прочитанных байт
12.  Приложение: получает результат
```

**8. Почему FUSE работает медленнее нативных kernel FS?**

Основные причины снижения производительности:
- **Context switching**: переключение kernel ↔ userspace на каждую операцию (~2-5 мкс overhead)
- **Копирование данных**: дополнительные копирования через `/dev/fuse`
- **Отсутствие direct I/O**: данные всегда проходят через userspace
- **Сериализация**: FUSE обрабатывает запросы последовательно
- **Memory allocation**: дополнительные выделения памяти в userspace

Из наших тестов: overhead 67-78% для мелких операций, 46% для больших файлов. 

**9. Какие преимущества дает разработка FS в userspace?**

- **Безопасность**: крах FUSE FS не роняет ядро
- **Отладка**: можно использовать gdb, valgrind, strace
- **Библиотеки**: доступ ко всем userspace библиотекам (libcurl, libssl)
- **Языки программирования**: Python, Go, Rust, не только C
- **Быстрая разработка**: нет необходимости пересобирать ядро
- **Переносимость**: один код работает на разных ОС

**10. Приведите примеры популярных FUSE файловых систем.**

- **sshfs** — монтирование удаленных директорий через SSH
- **GCS FUSE** — доступ к Google Cloud Storage как к локальной ФС
- **s3fs** — монтирование Amazon S3 buckets
- **NTFS-3G** — поддержка записи на NTFS в Linux
- **EncFS** — шифрующая файловая система
- **GVFS** — виртуальная ФС GNOME для FTP, SMB
- **ZFS FUSE** — пользовательская реализация ZFS

### File operations

**11. Что делает операция getattr() и когда она вызывается?**

`getattr()` возвращает атрибуты файла (аналог `stat()`).  Вызывается при:
- `ls -l` — для получения размера, прав, времени модификации
- `stat` — прямой запрос атрибутов
- Открытии файла — проверка существования и прав
- Навигации по директориям — проверка типа (файл/директория)

Возвращает структуру `struct stat` с полями: `st_mode`, `st_size`, `st_mtime`, `st_uid`, `st_gid`. 

**12. В чем разница между open() и create()?**

- **open()** — открывает существующий файл или создает с флагом `O_CREAT`
- **create()** — всегда создает новый файл с указанными правами

В FUSE:
```c
// Открытие существующего файла
static int myfs_open(const char *path, struct fuse_file_info *fi);

// Создание нового файла
static int myfs_create(const char *path, mode_t mode, struct fuse_file_info *fi);
```

`create()` автоматически вызывает `open()` после создания. 

**13. Почему read() принимает параметр offset?**

Offset указывает позицию в файле для чтения, что позволяет:
- **Random access**: читать любую часть файла без sequential чтения
- **Параллельное чтение**: несколько процессов читают разные части
- **mmap()**: отображение файла в память требует offset для page alignment
- **Эффективность**: база данных читает только нужные блоки

```c
// FUSE read с offset
static int myfs_read(const char *path, char *buf, size_t size, 
                     off_t offset, struct fuse_file_info *fi);
```

**14. Как readdir() возвращает список файлов?**

`readdir()` использует callback-функцию `filler` для добавления каждой записи:

```c
static int myfs_readdir(const char *path, void *buf, fuse_fill_dir_t filler,
                        off_t offset, struct fuse_file_info *fi) {
    // Добавляем стандартные записи
    filler(buf, ".", NULL, 0);
    filler(buf, "..", NULL, 0);
    
    // Добавляем файлы
    filler(buf, "file1.txt", NULL, 0);
    filler(buf, "subdir", NULL, 0);
    
    return 0;
}
```

Каждый вызов `filler()` добавляет одну запись в результат.

**15. Что должна возвращать getattr() для директории?**

Для директории `getattr()` должна установить:
- **st_mode**: `S_IFDIR | permissions` (например, `S_IFDIR | 0755`)
- **st_nlink**: количество subdirectories + 2 (.  и ..)
- **st_size**: 0 или размер директории (зависит от ФС)
- **st_uid/st_gid**: владелец директории

```c
stbuf->st_mode = S_IFDIR | 0755;
stbuf->st_nlink = 2; // .  и ..
stbuf->st_size = 4096; // размер блока
```

### Метаданные и атрибуты

**16.  Что такое атрибуты файла?  Приведите примеры.**

Атрибуты файла — метаданные, описывающие свойства файла:

**Стандартные атрибуты:**
- **Размер**: количество байт
- **Права доступа**: rwxrwxrwx (owner/group/others)
- **Владелец**: UID, GID
- **Временные метки**: atime, mtime, ctime
- **Тип**: обычный файл, директория, символическая ссылка

**Расширенные атрибуты (xattr):**
- **SELinux labels**: `security.selinux`
- **ACL**: `system.posix_acl_access`
- **Пользовательские**: `user.author`, `user.checksum`

**17. Что означают биты прав доступа (rwxrwxrwx)?**

9-битная маска прав доступа, разделенная на 3 группы:

```
rwx rwx rwx
│   │   └── Others (все остальные пользователи)
│   └────── Group (группа владельца)
└────────── Owner (владелец файла)
```

**Значение битов:**
- **r (4)**: read — чтение файла / просмотр директории
- **w (2)**: write — запись в файл / создание файлов в директории  
- **x (1)**: execute — выполнение файла / вход в директорию

**Примеры:**
- `755 (rwxr-xr-x)`: владелец — полные права, остальные — чтение+выполнение
- `644 (rw-r--r--)`: владелец — чтение+запись, остальные — только чтение

**18. Объясните разницу между mtime, atime и ctime.**

- **mtime** (modification time): время последнего изменения содержимого файла
  - Обновляется при `write()`, `truncate()`
  - Используется `make` для проверки актуальности
  
- **atime** (access time): время последнего чтения файла
  - Обновляется при `read()`, `open()`
  - Часто отключается (`noatime`) для производительности
  
- **ctime** (change time): время последнего изменения метаданных
  - Обновляется при `chmod()`, `chown()`, `rename()`
  - Не может быть изменена пользователем

**19.  Что такое hard link и как он отличается от symbolic link?**

**Hard link:**
- Дополнительное имя для существующего inode
- Все hard links равноправны
- Увеличивает счетчик ссылок (`st_nlink`)
- Не может ссылаться на директории или файлы на других файловых системах
- Файл удаляется только когда `st_nlink` становится 0

**Symbolic link:**
- Отдельный файл, содержащий путь к целевому файлу
- Может ссылаться на несуществующие файлы (broken link)
- Может ссылаться на директории и файлы на других ФС
- Имеет собственный inode

```bash
# Hard link
ln file. txt hardlink.txt

# Symbolic link  
ln -s file.txt symlink.txt
```

**20. Как FS определяет размер файла?**

Размер файла хранится в поле `st_size` структуры inode. Для разных типов файлов:

- **Обычные файлы**: количество байт данных
- **Директории**: размер метаданных (обычно размер блока)
- **Символические ссылки**: длина целевого пути
- **Устройства**: 0 или размер устройства
- **Sparse files**: логический размер может превышать физический

### Физическая организация

**21. Что такое блок в файловой системе?**

Блок — минимальная единица дискового пространства, которой оперирует файловая система. Обычно кратен размеру сектора диска (512 байт).

**Типичные размеры блоков:**
- **ext4**: 4KB (по умолчанию), 1KB-64KB
- **NTFS**: 4KB
- **ZFS**: переменный размер (512B-1MB)

**Преимущества больших блоков:**
- Меньше метаданных для хранения
- Эффективнее для больших файлов

**Недостатки:**
- Внутренняя фрагментация для мелких файлов

**22. Объясните принцип непрерывного размещения файлов (contiguous allocation).**

Файл размещается в последовательных блоках диска. 

**Структура:**
```
File: [start_block, length]
file. txt: [100, 5] → блоки 100,101,102,103,104
```

**Преимущества:**
- Быстрый sequential access
- Простое вычисление адреса: `start_block + offset`
- Минимальные метаданные

**Недостатки:**
- **Внешняя фрагментация**: сложно найти непрерывную область
- **Предварительное выделение**: нужно знать размер заранее
- Неэффективно для файлов переменного размера

**Использование:** CD-ROM, некоторые embedded системы. 

**23. Как работает организация через связанный список блоков (linked allocation)?**

Каждый блок файла содержит указатель на следующий блок. 

**Структура:**
```
Block 100: [data][ptr→150]
Block 150: [data][ptr→200]  
Block 200: [data][ptr→NULL]
```

**Преимущества:**
- Нет внешней фрагментации
- Файлы могут расти динамически

**Недостатки:**
- **Random access**: для чтения блока N нужно пройти весь список
- **Надежность**: поврежденный указатель = потерянная часть файла
- **Overhead**: указатели съедают место в блоках

**Вариация — FAT:**
Таблица указателей вынесена отдельно, что решает проблему random access.

**24. Что такое индексный узел (inode-based allocation)?**

Inode содержит прямые и косвенные указатели на блоки данных файла.

**Структура ext4 inode:**
```
Прямые указатели:    12 блоков (12 × 4KB = 48KB)
Одинарно косвенный:  1024 блока (4MB)
Двойно косвенный:    1M блоков (4GB)  
Тройно косвенный:    1G блоков (4TB)
```

**Преимущества:**
- **Fast random access**: прямой доступ к блоку по индексу
- **Компактность**: метаданные только в inode
- **Масштабируемость**: поддержка файлов до терабайт

**Недостатки:**
- Ограничение на количество прямых указателей
- Косвенные блоки добавляют уровни indirection

**25. Сравните ext4 и btrfs по структуре хранения данных.**

| Аспект | ext4 | btrfs |
|--------|------|-------|
| **Метаданные** | Фиксированные inode | B-tree структуры |
| **Extent-based** | Да (группы блоков) | Да (переменный размер) |
| **COW (Copy-on-Write)** | Нет | Да |
| **Снапшоты** | Нет | Да (мгновенные) |
| **Checksums** | Нет | Да (данные + метаданные) |
| **Compression** | Нет | Да (zlib, lzo, zstd) |
| **Deduplication** | Нет | Да |
| **RAID** | Программный | Встроенный |

**ext4** — простая, надежная, оптимизированная для производительности. 
**btrfs** — современная, feature-rich, оптимизированная для целостности данных.

### Производительность и оптимизация

**26. Почему большие файлы читаются быстрее, чем много мелких?**

**Факторы для больших файлов:**
- **Sequential I/O**: диск читает большие блоки эффективнее
- **Меньше syscalls**: один `read(1MB)` вместо 1000 × `read(1KB)`
- **Amortization overhead**: накладные расходы размазаны по большому объему
- **Prefetching**: ОС может предсказать следующие блоки

**Проблемы мелких файлов:**
- **Seek time**: каждый файл требует позиционирования головки
- **Metadata overhead**: больше операций с inode, directory entries
- **Context switches**: больше системных вызовов

**Из наших тестов:** throughput растет от 245 MB/s (1MB) до 780 MB/s (100MB).

**27. Что такое read-ahead и как он улучшает производительность?**

Read-ahead — это предварительное чтение данных, которые скорее всего понадобятся.

**Типы:**
- **Sequential read-ahead**: при чтении файла последовательно ОС читает больше блоков
- **Opportunistic read-ahead**: использование простоев диска

**Механизм:**
1. Детекция sequential access pattern
2. Увеличение размера read-ahead window
3. Асинхронное чтение в page cache
4. Приложение находит данные уже в памяти

**Настройка:**
```bash
# Просмотр текущего значения
cat /sys/block/sda/queue/read_ahead_kb

# Установка 1MB read-ahead
echo 1024 > /sys/block/sda/queue/read_ahead_kb
```

**28.  Как page cache ускоряет доступ к файлам?**

Page cache — это кеш файловых данных в оперативной памяти. 

**Механизм:**
1. При первом чтении файла данные загружаются в page cache
2. Повторные обращения читают из памяти (в тысячи раз быстрее)
3. Dirty pages записываются на диск асинхронно
4. LRU eviction при нехватке памяти

**Преимущества:**
- **Ускорение**: RAM vs SSD = 100:1, RAM vs HDD = 10000:1
- **Write coalescing**: объединение мелких записей
- **Shared cache**: разные процессы используют общий кеш

**Мониторинг:**
```bash
# Просмотр page cache
cat /proc/meminfo | grep -E "(Cached|Buffers)"

# Очистка page cache (для тестов)
echo 3 > /proc/sys/vm/drop_caches
```

**29. Почему запись на SSD быстрее, чем на HDD?**

**SSD преимущества:**
- **Отсутствие механики**: нет времени позиционирования головки (seek time ~10ms для HDD)
- **Random access**: время доступа ~0. 1ms vs ~10ms для HDD
- **Параллелизм**: множество flash chips работают одновременно
- **Высокие IOPS**: 50,000+ vs 150 для HDD

**Но:**
- **Write amplification**: из-за стирания блоков
- **Wear leveling**: ограниченное количество циклов записи

**Benchmarks:**
| Операция | SSD | HDD |
|----------|-----|-----|
| Sequential Read | 500 MB/s | 150 MB/s |
| Random Read | 400 MB/s | 1 MB/s |
| Random Write IOPS | 50,000 | 150 |

**30. Какие параметры влияют на производительность FUSE FS?**

**Системные параметры:**
- **big_writes**: увеличивает размер write запросов до 128KB
- **max_read**: максимальный размер read запроса
- **max_write**: максимальный размер write запроса
- **direct_io**: обходит page cache (для некеширующихся ФС)

**Архитектурные решения:**
- **Многопоточность**: обработка параллельных запросов
- **Batching**: объединение мелких операций
- **Кеширование**: уменьшение обращений к backend
- **Asynchronous I/O**: неблокирующие операции

**Пример оптимизации:**
```bash
# Монтирование с оптимизированными параметрами
fusermount -o big_writes,max_read=131072 ./myfs /mnt/point
```

## 6. Выводы

### Основные достижения

В ходе лабораторной работы была успешно изучена архитектура виртуальной файловой системы Linux и механизм FUSE. Реализованы три типа файловых систем в пространстве пользователя:

1. **Passthrough FS** — обеспечивает прозрачное проксирование операций с полным логированием
2. **Archive FS** — предоставляет read-only доступ к содержимому tar архивов как к обычной директории
3. **Monitoring FS** — собирает детальную статистику операций в реальном времени

Все файловые системы корректно обрабатывают основные операции (`getattr`, `readdir`, `open`, `read`, `write`, `create`, `unlink`, `mkdir`, `rmdir`) и успешно проходят функциональное тестирование.

### Технические находки

**1. Архитектура FUSE:**
Главное открытие — понимание двухуровневой архитектуры FUSE.  Каждый системный вызов проходит путь: приложение → VFS → FUSE kernel → `/dev/fuse` → FUSE daemon → backend, что объясняет inherent overhead технологии.

**2.  Производительность:**
Нагрузочные тесты выявили характерные особенности FUSE:
- Context switching добавляет 67-78% latency к мелким операциям
- Throughput для больших файлов (>100MB) имеет приемлемый overhead ~46%
- IOPS снижается в ~3 раза по сравнению с нативными ФС

**3. Метаданные и кеширование:**
Archive FS показала важность предварительной загрузки метаданных в память.  Полный парсинг tar архива при монтировании значительно ускоряет последующие операции навигации.

### Сложности и их решения

**1. Управление памятью:**
Archive FS потребовала аккуратной работы с libarchive для избежания memory leaks. Решение — явное освобождение ресурсов в деструкторах и обработка ошибок. 

**2. Многопоточность:**
Monitoring FS выявила race conditions при параллельном доступе к статистике. Решение — использование `pthread_mutex` для защиты критических секций.

**3.  Обработка путей:**
Все реализации потребовали тщательной нормализации путей (удаление `./`, обработка абсолютных/относительных путей) для корректной работы. 

**4. Эмуляция виртуальных файлов:**
Реализация файла `/. stats` в Monitoring FS потребовала особой логики в `getattr()` и `open()` для корректного отображения динамически генерируемого содержимого.

### Практическая ценность

Работа наглядно демонстрирует:
- **Гибкость FUSE** для быстрого прототипирования ФС
- **Trade-off между удобством разработки и производительностью**
- **Возможности интеграции** различных backend'ов (локальные файлы, архивы, сетевые ресурсы)
- **Важность профилирования** для выявления bottlenecks
