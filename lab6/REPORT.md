## 2. Теоретическая часть

### 2.1 Архитектура VFS и роль FUSE

**Virtual File System (VFS)** — это абстрактный слой в ядре Linux, предоставляющий единый интерфейс для работы с различными типами файловых систем (ext4, btrfs, NFS, FUSE и др.). VFS позволяет приложениям использовать одни и те же системные вызовы независимо от типа файловой системы.

**FUSE (Filesystem in Userspace)** позволяет создавать файловые системы в пространстве пользователя без написания кода для ядра. Драйвер FUSE в ядре перенаправляет VFS операции в userspace процесс через специальный протокол.

### 2.2 Схема взаимодействия

```
┌──────────────────────────────────────────────────────┐
│  Приложение (cat, ls, echo)                          │
│  Использует стандартные системные вызовы:            │
│  open(), read(), write(), stat()                     │
└────────────────────┬─────────────────────────────────┘
                     ↓
┌────────────────────────────────────────────────────────┐
│  VFS (Virtual File System) — ядро Linux                │
│  Единый интерфейс для всех файловых систем             │
└────────────────────┬───────────────────────────────────┘
                     ↓
┌────────────────────────────────────────────────────────┐
│  FUSE kernel module (/dev/fuse)                        │
│  Перенаправляет запросы в userspace                    │
└────────────────────┬───────────────────────────────────┘
                     ↓ (протокол FUSE)
┌────────────────────────────────────────────────────────┐
│  libfuse (userspace библиотека)                        │
│  Парсит запросы и вызывает callback функции            │
└────────────────────┬───────────────────────────────────┘
                     ↓
┌────────────────────────────────────────────────────────┐
│  Наша программа (myfuse)                               │
│  Реализует file operations: getattr, read, write, etc. │
│  Проксирует запросы в реальную файловую систему        │
└────────────────────────────────────────────────────────┘
```

### 2.3 Реализованные file operations

В рамках лабораторной работы были реализованы следующие операции:

| Операция   | Системный вызов | Описание                                      |
|------------|-----------------|-----------------------------------------------|
| `getattr`  | `stat()`        | Получение метаданных файла (размер, права)    |
| `readdir`  | `readdir()`     | Чтение содержимого директории                 |
| `open`     | `open()`        | Открытие файла                                |
| `read`     | `read()`        | Чтение данных из файла                        |
| `write`    | `write()`       | Запись данных в файл                          |

**1. Преобразование путей (utils.c)**

Функция `get_full_path()` преобразует FUSE путь (например, `/test.txt`) в абсолютный путь реальной файловой системы (`/tmp/fuse_source/test.txt`):

```c
void get_full_path(char *fullpath, const char *path) {
    if (strcmp(path, "/") == 0) {
        strcpy(fullpath, source_dir);
        return;
    }
    
    size_t len = strlen(source_dir);
    if (source_dir[len - 1] == '/') len--;
    
    strncpy(fullpath, source_dir, len);
    fullpath[len] = '\0';
    strcat(fullpath, path);
}
```

**2. Логирование операций (utils.c)**

Каждая операция логируется в формате `[YYYY-MM-DD HH:MM:SS] OPERATION: path (result: N)`:

```c
void log_operation(const char *op_name, const char *path, int result) {
    time_t timer;
    char buffer[26];
    struct tm* tm_info;

    time(&timer);
    tm_info = localtime(&timer);
    strftime(buffer, 26, "%Y-%m-%d %H:%M:%S", tm_info);

    fprintf(stderr, "[%s] %s: %s (result: %d)\n", 
            buffer, op_name, path, result);
}
```

**3. Пример реализации операции (operations.c)**

Операция `my_read()` демонстрирует типичную структуру:

```c
int my_read(const char *path, char *buf, size_t size, off_t offset, 
            struct fuse_file_info *fi) {
    int res;

    // Читаем из реального файла через сохранённый file descriptor
    res = pread(fi->fh, buf, size, offset);
    if (res == -1) {
        res = -errno;
    }

    // Логируем операцию
    log_operation("READ", path, res);
    return res;
}
```

## 6. Ответы на контрольные вопросы

### Архитектура файловых систем

**1. Что такое VFS (Virtual File System) и зачем она нужна?**

VFS — это абстрактный слой в ядре Linux, который предоставляет единый интерфейс для работы с различными файловыми системами. Без VFS каждое приложение должно было бы реализовывать поддержку каждого типа ФС (ext4, btrfs, NFS и т.д.). VFS позволяет использовать одни и те же системные вызовы (`open`, `read`, `write`) независимо от типа файловой системы.

**2. Объясните разницу между inode, dentry и file descriptor.**

- **inode** — структура в ФС, хранящая метаданные файла: размер, права доступа, временные метки, указатели на блоки данных. Каждый файл имеет уникальный inode number.
- **dentry** (directory entry) — запись в кеше директорий, связывающая имя файла с его inode. Ускоряет поиск файлов по пути.
- **file descriptor** — целочисленный идентификатор открытого файла в процессе. Указывает на структуру `struct file` в ядре, которая содержит текущую позицию чтения/записи и флаги доступа.

**3. Что хранится в структуре `struct inode`?**

- Размер файла (`i_size`)
- Права доступа (`i_mode`)
- Владелец и группа (`i_uid`, `i_gid`)
- Временные метки: `i_atime` (последний доступ), `i_mtime` (изменение данных), `i_ctime` (изменение метаданных)
- Количество ссылок (`i_nlink`)
- Указатели на блоки данных (`i_blocks`)
- Операции для работы с файлом (`i_op`, `i_fop`)

**4. Что такое superblock и какую информацию он содержит?**

Superblock — это структура, описывающая файловую систему в целом. Содержит:
- Размер блока данных
- Общее количество блоков и свободных блоков
- Указатель на root inode
- Magic number (идентификатор типа ФС)
- Флаги монтирования (read-only, noexec и т.д.)

**5. Как работает кеш dentry и зачем он нужен?**

Dentry cache (dcache) кеширует результаты поиска файлов по пути. Когда приложение обращается к `/home/user/file.txt`, ядро должно разрешить каждый компонент пути: `/` → `home` → `user` → `file.txt`. Dcache хранит эти соответствия в памяти, избегая повторных обращений к диску. Это критично для производительности, так как многие приложения обращаются к одним и тем же файлам многократно.

### FUSE

**6. Как FUSE взаимодействует с ядром Linux?**

FUSE использует драйвер в ядре (`/dev/fuse`) и протокол передачи сообщений. Когда VFS получает системный вызов для FUSE ФС, драйвер формирует запрос и отправляет его через устройство `/dev/fuse` в userspace. Процесс FUSE (демон) читает запрос, обрабатывает его (вызывает соответствующий callback), и отправляет ответ обратно через `/dev/fuse`. Ядро возвращает результат приложению.

**7. Опишите путь системного вызова `read()` в FUSE FS.**

1. Приложение вызывает `read(fd, buf, size)`
2. Системный вызов попадает в ядро → VFS
3. VFS определяет, что файл принадлежит FUSE ФС
4. FUSE kernel module формирует FUSE_READ запрос
5. Запрос отправляется через `/dev/fuse` в userspace
6. libfuse читает запрос и вызывает `my_read()`
7. `my_read()` выполняет реальный `pread()` на файле
8. Данные копируются обратно через `/dev/fuse`
9. Ядро копирует данные в буфер приложения
10. `read()` возвращает количество прочитанных байт

**8. Почему FUSE работает медленнее нативных kernel FS?**

Три основные причины:
- **Context switch:** Каждая операция требует переключения kernel ↔ userspace
- **Копирование данных:** Данные копируются дважды: диск → kernel → userspace → kernel → приложение
- **Отсутствие оптимизаций:** Kernel ФС могут использовать прямой доступ к страничному кешу, zero-copy техники и специальные оптимизации ядра

**9. Какие преимущества дает разработка FS в userspace?**

- **Безопасность:** Ошибка в FUSE не вызовет kernel panic
- **Простота разработки:** Можно использовать обычные библиотеки, отладчики (gdb), sanitizers
- **Быстрая итерация:** Не нужна перезагрузка системы после изменений
- **Портируемость:** FUSE доступна на Linux, macOS, FreeBSD
- **Гибкость:** Можно реализовать экзотическую логику (шифрование, сетевые ФС, виртуальные ФС)

**10. Приведите примеры популярных FUSE файловых систем.**

- **sshfs** — монтирование удалённой директории через SSH
- **GCS FUSE** — доступ к Google Cloud Storage как к локальной ФС
- **s3fs** — монтирование Amazon S3 bucket
- **EncFS / gocryptfs** — шифрующие файловые системы
- **NTFS-3G** — поддержка NTFS на Linux
- **ZipFS / ArchiveMount** — просмотр архивов как директорий

## File operations

**11. Что делает операция `getattr()` и когда она вызывается?**

`getattr()` возвращает метаданные файла (аналог `stat()`): размер, права, временные метки, тип файла. Вызывается при:
- `ls -l` — для получения размера и прав
- `stat filename` — явный запрос метаданных
- Открытии файла — проверка существования и прав
- Чтении директории — для заполнения полей в `struct stat`
    
**12. В чем разница между `open()` и `create()`?**

- `open()` — открывает существующий файл. Если файла нет и не указан флаг `O_CREAT`, возвращает ошибку.
- `create()` — создаёт новый файл и сразу открывает его. Эквивалентно `open(path, O_CREAT | O_WRONLY | O_TRUNC, mode)`.

В FUSE: `create()` вызывается при `open()` с флагом `O_CREAT`. Это оптимизация — объединение двух операций в одну.

**13. Почему `read()` принимает параметр `offset`?**

Для поддержки позиционного чтения (pread). Приложение может читать с произвольной позиции без изменения file pointer (`lseek`). Это важно для:
- Многопоточности (разные потоки читают разные части файла)
- Эффективности (избегаем лишних `lseek` вызовов)
- Прозрачности (FUSE не управляет file pointer, это делает ядро)

**14. Как `readdir()` возвращает список файлов?**

`readdir()` вызывается с callback функцией `filler`. Для каждого файла в директории вызывается `filler(buf, filename, &stat, 0)`. `filler` добавляет запись в буфер, который VFS затем возвращает приложению. Мы не формируем массив вручную — libfuse управляет памятью.

**15. Что должна возвращать `getattr()` для директории?**

`struct stat` с полями:
- `st_mode = S_IFDIR | 0755` — это директория с правами rwxr-xr-x
- `st_nlink = 2` (минимум: `.` и `..`)
- `st_size` — обычно размер блока (например, 4096)
- Временные метки (`st_mtime`, `st_atime`, `st_ctime`)

## Метаданные и атрибуты

**16. Что такое атрибуты файла? Приведите примеры.**

Атрибуты (метаданные) — это информация о файле, не являющаяся его содержимым:
- **Основные:** размер, права доступа, владелец, временные метки
- **Расширенные (xattr):** `user.comment`, `security.selinux`
- **Специальные флаги:** immutable (неизменяемый), append-only

**17. Что означают биты прав доступа (rwxrwxrwx)?**

Три триплета по 3 бита: владелец / группа / остальные.
- **r** (4) — read (чтение)
- **w** (2) — write (запись)
- **x** (1) — execute (выполнение / вход в директорию)

Пример: `0755` = `rwxr-xr-x` = владелец может всё, остальные только читать и выполнять.

**18. Объясните разницу между mtime, atime и ctime.**

- **atime** (access time) — время последнего чтения файла
- **mtime** (modification time) — время последнего изменения содержимого
- **ctime** (change time) — время последнего изменения метаданных (права, владелец) или содержимого

Важно: `ctime` НЕ является временем создания! Время создания (birth time) есть не во всех ФС.

**19. Что такое hard link и как он отличается от symbolic link?**

- **Hard link** — дополнительное имя для существующего inode. Оба файла указывают на одни и те же данные. Удаление одного не удаляет другой (данные удаляются когда `nlink` → 0). Работает только внутри одной ФС.
- **Symbolic link (symlink)** — файл, содержащий путь к другому файлу. Если оригинал удалён, symlink "сломан". Работает между разными ФС.

**20. Как ФС определяет размер файла?**

Размер хранится в inode в поле `i_size`. При записи данных за пределы текущего размера, `i_size` увеличивается. Размер != занимаемое место: sparse files могут иметь большой `i_size` но занимать мало блоков (дыры заполнены нулями виртуально).

## Физическая организация

**21. Что такое блок в файловой системе?**

Блок — минимальная единица выделения дискового пространства. Типичные размеры: 512 байт, 4 KB, 8 KB. Даже файл в 1 байт занимает целый блок. Блоки группируются в allocation groups для эффективности.

**22. Объясните принцип непрерывного размещения файлов (contiguous allocation).**

Файл занимает последовательные блоки на диске. Достоинства: быстрое последовательное чтение (нет seeks). Недостатки: фрагментация (нельзя расширить файл если следующие блоки заняты), нужно знать размер заранее. Используется в CD-ROM, ISO образах.

**23. Как работает организация через связанный список блоков (linked allocation)?**

Каждый блок содержит указатель на следующий блок. Достоинства: файл может расти динамически, нет фрагментации. Недостатки: медленный случайный доступ (нужно пройти по цепочке), потеря одного блока = потеря остальной части файла. Используется в FAT.

**24. Что такое индексный узел (inode-based allocation)?**

Файл представлен inode, который содержит указатели на блоки данных. В ext4: 12 прямых указателей, 1 одинарно-косвенный, 1 двойной, 1 тройной. Позволяет эффективно хранить как маленькие, так и огромные файлы. Быстрый случайный доступ к любому блоку.

**25. Сравните ext4 и btrfs по структуре хранения данных.**

- **ext4:** inode-based, использует extent trees (непрерывные диапазоны блоков вместо отдельных блоков). Журналирование метаданных.
- **btrfs:** copy-on-write (CoW) B-trees, встроенная поддержка snapshots, checksums для всех данных, compression, RAID. Более гибкая, но сложнее.

## Производительность и оптимизация

**26. Почему большие файлы читаются быстрее, чем много мелких?**

- **Меньше overhead на метаданные:** 1 операция vs 1000 операций
- **Последовательный доступ:** Диск эффективен при чтении больших блоков подряд
- **Меньше context switches:** В FUSE каждый файл = отдельный OPEN/READ/CLOSE цикл
- **Эффективность кеширования:** Большой файл может использовать page cache полностью

Наши тесты: 100 MB файл @ 727 MB/s vs 1000 файлов по 14 байт @ 3.3 сек = 0.004 MB/s

**27. Что такое read-ahead и как он улучшает производительность?**

Read-ahead — упреждающее чтение: когда приложение читает блок N, ядро автоматически читает блоки N+1, N+2... в кеш. Для последовательного чтения это даёт огромный выигрыш: к моменту запроса следующего блока, он уже в памяти. Размер read-ahead динамически подстраивается.

**28. Как page cache ускоряет доступ к файлам?**

Page cache хранит содержимое файлов в оперативной памяти. При повторном чтении того же файла, данные берутся из RAM вместо диска (скорость ~10 GB/s vs ~200 MB/s для SSD). При записи данные сначала попадают в кеш (write-back), затем асинхронно сбрасываются на диск (dirty pages).

**29. Почему запись на SSD быстрее, чем на HDD?**

- **Нет механических частей:** SSD использует flash память, нет времени на перемещение головки (seek time ~10 ms на HDD)
- **Параллелизм:** SSD может писать в несколько каналов одновременно
- **Случайная запись:** На SSD случайная запись почти так же быстра, как последовательная

Но: SSD имеет ограниченный ресурс записи (P/E cycles), HDD долговечнее для архивных данных.

**30. Какие параметры влияют на производительность FUSE FS?**

- **Размер блока чтения/записи:** Большие блоки → меньше context switches
- **Многопоточность:** libfuse поддерживает multi-threading (`-o max_threads=N`)
- **Direct I/O:** Отключение page cache (`-o direct_io`) уменьшает копирование
- **Кеширование метаданных:** `-o attr_timeout=N` (кешировать getattr результаты)
- **Write-back cache:** `-o writeback_cache` (буферизация записей)
- **Эффективность callback'ов:** Оптимизация кода в userspace обработчиках
