## 1. Цель работы

Целью данной лабораторной работы является освоение принципов работы виртуальной файловой системы в Linux и получение практических навыков создания собственных файловых систем с использованием библиотеки FUSE. В рамках работы необходимо разработать три различные ФС:

- **Passthrough FS** — проброс операций к реальной директории
- **Archive FS** — представление tar-архива в виде папки (только чтение)
- **Monitoring FS** — ФС со сбором статистики и виртуальным файлом `.stats`

## 1.1. Сборка и запуск

### Требования

- Linux с поддержкой FUSE
- Библиотека libfuse3 (`apt install libfuse3-dev` или `dnf install fuse3-devel`)
- GCC и pkg-config

### Сборка

```bash
make
```

### Запуск

```bash
# Passthrough FS
mkdir -p /tmp/source /tmp/mountpoint
./myfuse passthrough /tmp/source /tmp/mountpoint -f

# Archive FS
./myfuse archive myarchive.tar /tmp/mountpoint -f

# Monitoring FS
./myfuse monitor /tmp/source /tmp/mountpoint -f
```

### Размонтирование

```bash
fusermount -u /tmp/mountpoint
```

## 2. Теория

### 2.1. Виртуальная файловая система (VFS)

VFS представляет собой промежуточный уровень абстракции в ядре Linux. Его главная задача — предоставить универсальный программный интерфейс для работы с любыми файловыми системами.

**Ключевые структуры данных VFS:**

| Структура | Назначение |
|-----------|------------|
| superblock | Содержит общую информацию о смонтированной ФС |
| inode | Хранит метаданные конкретного файла |
| dentry | Обеспечивает связь между именем и inode |
| file | Представляет открытый файловый дескриптор |

### 2.2. Механизм FUSE

FUSE (Filesystem in Userspace) даёт возможность реализовывать файловые системы в пользовательском пространстве, без необходимости писать код ядра.

**Схема обработки запроса:**

```
Программа пользователя
       ↓
     VFS (ядро)
       ↓
  Модуль FUSE в ядре
       ↓
   /dev/fuse
       ↓
  libfuse (userspace)
       ↓
  Наш обработчик
```

**Плюсы подхода:** безопасная разработка, простая отладка, можно использовать обычные библиотеки.

**Минусы:** дополнительные накладные расходы из-за переключений между ядром и userspace.

## 3. Практическая часть

### Задание A: Passthrough FS

Данная файловая система работает как прозрачный прокси — все операции просто передаются на реальную файловую систему.

**Реализованные операции:**
- `getattr` — получение атрибутов
- `readdir` — чтение содержимого директории
- `open`, `read`, `write` — работа с файлами
- `create`, `unlink` — создание и удаление файлов
- `mkdir`, `rmdir` — операции с каталогами

Добавлено логирование всех операций в stderr для отладки.

**Тестовые команды:**

```bash
# Создание файла
echo "test data" > /mnt/fuse/myfile.txt

# Чтение
cat /mnt/fuse/myfile.txt

# Удаление
rm /mnt/fuse/myfile.txt
```

---

### Задание B: Archive FS

Файловая система для просмотра содержимого tar-архивов без распаковки. Работает только на чтение.

**Что сделано:**
- Парсинг заголовков формата POSIX tar (512 байт на запись)
- Хранение информации о файлах в памяти (имя, размер, смещение)
- Операции `getattr`, `readdir`, `read`
- Блокировка любых попыток записи

**Использование:**

```bash
./myfuse archive myarchive.tar /mnt/archive -f
ls /mnt/archive/
cat /mnt/archive/readme.txt
```

### Задание C: Monitoring FS

Расширение Passthrough FS с добавлением сбора статистики. Вся статистика доступна через виртуальный файл `/.stats`.

**Собираемые метрики:**
- Количество вызовов `open`
- Количество операций чтения и записи
- Общий объём прочитанных данных (байт)
- Общий объём записанных данных (байт)

**Пример вывода:**

```bash
$ cat /mnt/fuse/.stats
open: 5
read: 12
write: 3
bytes_read: 8192
bytes_written: 256
```

## 5. Контрольные вопросы

### Блок: VFS

**1. Что представляет собой VFS и какова её роль?**

VFS — это уровень абстракции, позволяющий ядру работать с разными типами файловых систем через единый интерфейс. Приложения используют стандартные вызовы (open, read, write), а VFS направляет их к нужной реализации — будь то ext4, NTFS или сетевая ФС. Благодаря этому можно монтировать разные ФС без изменения приложений.

**2. Чем отличаются inode, dentry и file descriptor?**

- **inode** — структура с метаданными файла (размер, права, указатели на блоки данных)
- **dentry** — элемент кеша имён, связывающий путь с inode
- **fd** — дескриптор, который процесс получает при открытии файла; содержит текущую позицию и флаги

Грубо говоря: inode описывает файл на диске, dentry — его имя в дереве каталогов, fd — сессию работы с файлом в конкретном процессе.

**3. Какие данные содержит структура inode?**

Режим доступа (тип + права), идентификаторы владельца (UID/GID), размер, временные метки (atime/mtime/ctime), счётчик жёстких ссылок, указатели на блоки данных (прямые и косвенные). Эта информация позволяет системе находить и контролировать доступ к содержимому файла.

**4. Что такое superblock?**

Superblock — это метаинформация обо всей файловой системе целиком: размер блока, общее количество блоков и inodes, число свободных ресурсов, UUID, состояние ФС. Читается при монтировании и критически важен для работы ФС.

**5. Для чего нужен dentry cache?**

Кеш dentry (dcache) сохраняет результаты разбора путей. Когда программа обращается к `/home/user/file.txt`, VFS ищет каждый компонент пути. Кеш позволяет избежать повторных обращений к диску при частом доступе к одним и тем же путям.

### Блок: FUSE

**6. Как FUSE взаимодействует с ядром?**

В ядре загружается модуль fuse.ko, который регистрирует специальный тип ФС. При обращении к смонтированной FUSE-директории запросы передаются через устройство /dev/fuse в userspace-процесс, где библиотека libfuse вызывает соответствующие callback-функции. Ответ возвращается тем же путём.

**7. Как проходит системный вызов read() в FUSE?**

1. Приложение вызывает read()
2. Ядро определяет, что это FUSE-монтирование
3. Запрос сериализуется и отправляется в /dev/fuse
4. Демон FUSE читает запрос и вызывает наш обработчик
5. Данные возвращаются через /dev/fuse обратно в ядро
6. Ядро передаёт результат приложению

**8. Почему FUSE медленнее нативных ФС?**

Основные причины — переключения контекста между ядром и userspace, копирование данных через границу пространств, накладные расходы на IPC. Особенно это заметно при большом количестве мелких операций.

**9. В чём преимущества userspace-разработки ФС?**

Ошибки в коде не приводят к kernel panic, можно использовать обычные отладчики и любые библиотеки, быстрее цикл разработки. Подходит для прототипов, сетевых ФС, работы с архивами и шифрованием.

**10. Примеры популярных FUSE-систем**

- **SSHFS** — монтирование удалённых директорий по SSH
- **s3fs** — работа с Amazon S3 как с локальной папкой  
- **NTFS-3G** — полноценная поддержка NTFS в Linux
- **rclone mount** — облачные хранилища
- **encfs** — шифрование на лету

### Блок: Файловые операции

**11. Что делает getattr()?**

Заполняет структуру stat информацией о файле: тип, права, размер, владелец, временные метки. Вызывается очень часто — при ls, stat, перед открытием файла.

**12. Разница между open() и create()?**

`open()` открывает существующий файл, `create()` — создаёт новый (и сразу открывает его). В FUSE это разные callback'и: в create() нужно создать ресурс и вернуть дескриптор.

**13. Зачем read() принимает offset?**

Для поддержки произвольного доступа к файлу. Можно читать с любой позиции, не меняя внутреннее состояние дескриптора. Это важно для многопоточности и mmap.

**14. Как работает readdir()?**

Получает буфер и функцию-заполнитель (filler). Мы перебираем содержимое директории и для каждого элемента вызываем filler с именем файла. Важно не забыть про "." и "..".

**15. Что должен возвращать getattr() для директории?**

Тип S_IFDIR, права с битом исполнения (для возможности входа), st_nlink минимум 2, корректные временные метки. Без правильных атрибутов ls и cd работать не будут.

### Блок: Атрибуты и метаданные

**16. Что такое атрибуты файла?**

Свойства, хранящиеся в inode: размер, права доступа, владелец, группа, временные метки, тип файла, количество ссылок. Некоторые ФС поддерживают расширенные атрибуты (xattr).

**17. Как интерпретировать биты rwxrwxrwx?**

Три группы по три бита: владелец, группа, остальные. r — чтение, w — запись, x — выполнение (для файлов) или вход (для директорий). Например, 755 = rwxr-xr-x.

**18. Чем отличаются atime, mtime, ctime?**

- **atime** — время последнего чтения
- **mtime** — время последнего изменения содержимого
- **ctime** — время изменения метаданных (включая права, владельца)

При записи меняются mtime и ctime, при chmod — только ctime.

**19. Hard link vs symbolic link?**

Hard link — ещё одно имя для того же inode, файл удаляется только когда удалены все ссылки. Symbolic link — отдельный файл со ссылкой на путь, может указывать на несуществующий файл и работает между разными ФС.

**20. Откуда берётся размер файла?**

Хранится в поле st_size структуры inode. Обновляется при записи и truncate. Для sparse-файлов может быть больше реально занятого места.

### Блок: Организация хранения

**21. Что такое блок?**

Минимальная единица выделения места в ФС. Обычно 4 КБ. Даже файл в 1 байт занимает целый блок. Блочная организация упрощает управление пространством.

**22. Непрерывное размещение (contiguous)**

Файлу выделяется непрерывная последовательность блоков. Плюс — быстрое последовательное чтение. Минус — фрагментация и сложность с расширением файла.

**23. Связанный список блоков**

Каждый блок хранит указатель на следующий. Легко расширять файл, но плохо для случайного доступа — нужно пройти всю цепочку. Пример: FAT.

**24. Индексная организация (inode)**

Inode содержит массив указателей: прямые (на блоки данных) и косвенные (на блоки с указателями). Баланс между скоростью доступа к началу файла и поддержкой больших размеров.

**25. Сравнение ext4 и btrfs**

**Ext4:** журналируемая ФС, inode-структура, extent-аллокация, проверенная стабильность, хорошая производительность.

**Btrfs:** copy-on-write, встроенные снапшоты и сжатие, дедупликация, RAID, B-tree структура. Более гибкая, но сложнее в настройке.

### Блок: Производительность

**26. Почему большие файлы читаются быстрее мелких?**

Меньше накладных расходов на открытие/закрытие, меньше обращений к метаданным, последовательное чтение эффективнее для дисков. На HDD особенно критичны seek-операции.

**27. Что такое read-ahead?**

Упреждающее чтение — ядро загружает в кеш блоки, которые скорее всего понадобятся следующими при последовательном чтении. Снижает время ожидания I/O.

**28. Роль page cache**

Кеширует страницы файлов в RAM. Повторные чтения обслуживаются из памяти без обращения к диску. Также буферизует записи перед сбросом на диск.

**29. SSD vs HDD по скорости записи**

SSD не имеет механических частей, нет задержек на позиционирование головки. Случайный доступ почти такой же быстрый, как последовательный. HDD выигрывает только при потоковых операциях большого объёма.

**30. От чего зависит производительность FUSE?**

Частота переключений контекста, размер буферов, многопоточность демона, опции монтирования (big_writes, direct_io), качество кеширования на стороне userspace, сетевые задержки для удалённых бэкендов.
