## 2. Теоретическая часть (кратко)

### VFS

Virtual File System — абстрактный слой в ядре Linux, который предоставляет единый интерфейс для разных ФС. Ключевые структуры:

* **superblock** — информация о ФС в целом;
* **inode** — метаданные файла (размер, права, временные метки);
* **dentry** — кеш имен директорий;
* **file** — структура открытого файла (позиция, дескриптор).

### FUSE

FUSE (Filesystem in Userspace) позволяет реализовывать файловые системы в userspace. Поток вызовов:

```
приложение → syscall → VFS → FUSE kernel module → /dev/fuse → libfuse → userspace-программа (ваша) 
```

Преимущества: простота разработки и отладки, безопасность; недостаток — overhead (context switches, копирование).

### Реализованные file operations

В проекте реализованы:
`getattr`, `readdir`, `open`, `read`, `write`, `create`, `unlink`, `mkdir`, `rmdir`.

### Ключевые идеи реализации

* **Passthrough**: все операции проксируются в реальную директорию `source_dir`. Для любого `path` формируется `fullpath = base_path + path`; затем вызываются соответствующие POSIX-вызовы (`open`, `pread`, `pwrite`, `lstat`, `opendir` и т.д.).
* **ROT13 (вариант B)**: при `write()` содержимое преобразуется `rot13` и записывается зашифрованным на диск; при `read()` — данные читаются с диска и обратно преобразуются `rot13` перед отдачей в userspace.
* **Uppercase (вариант C)**: `read()` делает `uppercase_inplace()` над прочитанными байтами; `write()` — записывает данные как есть.
* **Логирование**: все операции логируются в `stderr` в формате:
  `[YYYY-MM-DD HH:MM:SS] OPERATION: path (result: <code/bytes/0>)` (реализовано в `utils.c:log_operation`).
* **Безопасность**: `build_fullpath()` проверяет, что итоговый `realpath` находится внутри `g_base_path` (профилактика path-traversal). Для create-операций проверяется родительский каталог.
* **Обработка ошибок**: при ошибке системного вызова возвращается `-errno`.

### Важные функции

* `init_fuse_environment(const char *source_dir, const char *mode_str)` — сохраняет `g_base_path`, устанавливает режим (passthrough/rot13/upper).
* `build_fullpath(const char *path, char *out, size_t outlen, int allow_nonexistent)` — безопасное построение пути.
* `rot13_inplace(char *buf, size_t n)` — ROT13-преобразование.
* `uppercase_inplace(char *buf, size_t n)` — перевод в верхний регистр.

## 4. Сборка и запуск (инструкция)

### Сборка

В корне проекта:

```bash
make
```

Makefile предполагает наличие `pkg-config` и `fuse3` (Linux). В результате появится бинарник `myfuse`.

### Запуск

Примеры:

```bash
# Создать директории
mkdir -p /tmp/source /tmp/mnt

# Запуск в режиме passthrough (по умолчанию)
./myfuse /tmp/source /tmp/mnt -f

# Запуск в режиме rot13
./myfuse /tmp/source /tmp/mnt --mode=rot13 -f

# Запуск в режиме upper
./myfuse /tmp/source /tmp/mnt --mode=upper -f
```

* `-f` — foreground (полезно для отладки).
* Для размонтирования:

```bash
fusermount -u /tmp/mnt
# либо
umount /tmp/mnt
```

## 5. Тестирование и примеры

### Базовые проверки

1. Создать файл через FUSE:

```bash
echo "Hello FUSE" > /tmp/mnt/test.txt
```

Логи (пример):

```
[2025-11-26 22:01:15] CREATE: /test.txt (result: 0)
[2025-11-26 22:01:15] WRITE: /test.txt (result: 11)
```

2. Прочитать:

```bash
cat /tmp/mnt/test.txt
```

Лог:

```
[2025-11-26 22:01:20] OPEN: /test.txt (result: 0)
[2025-11-26 22:01:20] READ: /test.txt (result: 11)
Hello FUSE
```

### ROT13 (пример)

Запуск:

```bash
./myfuse /tmp/source /tmp/mnt --mode=rot13 -f
echo "Hello" > /tmp/mnt/secret.txt
```

На диске (`/tmp/source/secret.txt`):

```
Uryyb
```

Через FUSE:

```
$ cat /tmp/mnt/secret.txt
Hello
```

### Uppercase (пример)

Запуск:

```bash
./myfuse /tmp/source /tmp/mnt --mode=upper -f
echo "hello world" > /tmp/source/sample.txt
cat /tmp/mnt/sample.txt
# => HELLO WORLD
```

## 7. Ответы на контрольные вопросы

### Архитектура файловых систем

1. **Что такое VFS и зачем?**
   VFS — абстракция в ядре, позволяющая работать с разными ФС единообразно (единный набор syscalls).
2. **Разница между inode, dentry и file descriptor?**
   `inode` — метаданные файла; `dentry` — запись в кеше имен (имя→inode); `file descriptor` — процессный дескриптор открытого файла (структура `file`).
3. **Что хранится в `struct inode`?**
   Информация о файле: размер, права, владельцы, номера блоков/указатели на данные, временные метки.
4. **Что такое superblock?**
   Метаданные файловой системы: размер, тип, информация о блоках, состояние ФС.
5. **Как работает кеш dentry и зачем?**
   Кеширует соответствия имени→inode для ускорения поиска файлов (уменьшает обращения к диску).

### FUSE

6. **Как FUSE взаимодействует с ядром?**
   FUSE kernel module перехватывает VFS-вызовы и передаёт их через `/dev/fuse` в userspace-процесс (libfuse).
7. **Путь `read()` в FUSE FS?**
   Программа → syscall read → VFS → FUSE kernel → /dev/fuse → libfuse → callback `read()` в userspace → ответ обратно.
8. **Почему FUSE медленнее kernel FS?**
   Доп. контекстные переключения, копирование данных между пространствами, IPC overhead.
9. **Преимущества разработки в userspace?**
   Простая отладка, отсутствие риска kernel panic, возможность использовать обычные юзер-ленговые библиотеки.
10. **Примеры FUSE-FS?**
    sshfs, rclone/gcsfuse, ntfs-3g, encfs.

### File operations

11. **Что делает `getattr()`?**
    Заполняет `struct stat` — метаданные файла; вызывается при `stat`, `ls -l`, и т.д.
12. **Разница `open()` и `create()`?**
    `open()` открывает существующий файл; `create()` создаёт новый файл (и обычно открывает его).
13. **Почему `read()` имеет `offset`?**
    Чтобы читать данные из произвольной позиции файла без изменения текущей позиции (random access).
14. **Как `readdir()` возвращает список?**
    Через вызов `filler(buf, name, &st, off)` для каждого имени.
15. **Что должна возвращать `getattr()` для директории?**
    `st_mode` с битом `S_IFDIR`, корректный `st_nlink`, `st_size` (обычно 4096) и права.

### Метаданные и атрибуты

16. **Что такое атрибуты файла?**
    Права, размер, владельцы, временные метки (atime/mtime/ctime), тип файла.
17. **Что означают биты `rwxrwxrwx`?**
    Права чтения/записи/выполнения для владельца, группы и остальных.
18. **Разница mtime, atime, ctime?**
    `atime` — время последнего доступа; `mtime` — время последней модификации содержимого; `ctime` — время последнего изменения метаданных/статуса.
19. **Что такое hard link и как отличается от symlink?**
    Hard link — дополнительное имя для того же inode; symlink — отдельный файл, содержащий путь к другому файлу.
20. **Как FS определяет размер файла?**
    По полю `st_size` в inode — число байт данных.

### Физическая организация

21. **Что такое блок?**
    Минимальная единица хранения на диске (обычно 4KB).
22. **Принцип contiguous allocation?**
    Файл хранится в последовательных блоках — простая схема, быстрая для чтения, но вызывает фрагментацию.
23. **Linked allocation?**
    Блоки связаны указателями, каждый блок указывает на следующий (подходит для последовательного доступа).
24. **inode-based allocation?**
    Inode содержит указатели на блоки (прямые/непрямые), как в ext/fs — гибко и эффективно.
25. **Сравнение ext4 vs btrfs**
    ext4 — простая, проверенная, журналируемая; btrfs — copy-on-write, снапшоты, встроенная проверка целостности, более сложна.

### Производительность и оптимизация

26. **Почему большие файлы читаются быстрее?**
    Меньше syscall'ов и накладных расходов на переключения; лучшая эффективность read-ahead / sequential IO.
27. **Что такое read-ahead?**
    Чтение дополнительных блоков заранее для уменьшения ожиданий при последовательном доступе.
28. **Как page cache ускоряет доступ?**
    Хранит страницы файла в оперативной памяти; последующие чтения идут из RAM, без диска.
29. **Почему запись на SSD быстрее, чем HDD?**
    SSD не имеют механического перемещения головки/ротации — низкие задержки и высокая случайная IOPS.
30. **Какие параметры влияют на производительность FUSE FS?**
    Частота мелких операций, размер буферов, overhead IPC, настройки mount (direct_io, max_read), реализация в userspace (синхронная/асинхронная обработка).
