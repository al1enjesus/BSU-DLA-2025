## 1. Цель работы

Цель лабораторной работы — изучить архитектуру виртуальной файловой системы (VFS) Linux, освоить применение пользовательских файловых систем, реализованных через FUSE (Filesystem in Userspace), и получить практический опыт в создании собственных FUSE-файловых систем: passthrough FS, модифицирующих и анализирующих данные файловых систем.


## 2. Теоретическая часть

### 2.1. Virtual File System (VFS)

VFS — это абстрактный слой ядра Linux, скрывающий различия между файловыми системами. Через VFS любые программы взаимодействуют с файлами посредством единых системных вызовов (`open`, `read`, `write`, `stat`, и т.д.), независимо от того, где физически хранятся данные — на ext4, btrfs, NFS или FUSE.

**Ключевые структуры VFS:**

* **superblock** — описание файловой системы (размеры блоков, ссылки на корневой inode и др.);
* **inode** — метаданные файла: размер, права, временные метки, тип;
* **dentry** — элемент кэша имён, связывает имя файла и inode;
* **file** — структура открытого файла, содержащая позицию чтения/записи и флаги.

### 2.2. Архитектура FUSE

FUSE позволяет создавать файловые системы в пользовательском пространстве.
Поток выполнения операций:

```
Программа → syscall → VFS → FUSE kernel module → /dev/fuse → libfuse → Ваша программа
```

**Преимущества FUSE:**

* безопасная разработка, вне ядра;
* использование библиотек userspace;
* удобство отладки.

**Недостатки:**

* накладные расходы на переходы между kernel space и userspace;
* дополнительное копирование данных.

### 2.3. Основные операции FUSE

FUSE предоставляет структуру `fuse_operations`. В рамках работы реализованы:

* `getattr` — получение метаданных;
* `readdir` — чтение содержимого директории;
* `open`, `read`, `write` — базовые операции;
* `create`, `unlink` — управление файлами;
* `mkdir`, `rmdir` — управление директориями.



## 3. Ход выполнения лабораторной работы

### 3.1. Задание A — Passthrough FUSE FS

### Реализация

Была реализована классическая passthrough-файловая система: любая операция, полученная от VFS, перенаправляется к реальной файловой системе. Основа — построение полного пути к файлу:

```
/mnt/fuse/path → /tmp/source/path
```

Каждая операция логируется в формате:

```
[TIMESTAMP] OPERATION: path (result)
```

Примеры реализованных функций:

* `passthrough_getattr()` вызывает `lstat` реального файла;
* `passthrough_read()` использует `open + pread`;
* `passthrough_write()` использует `open + pwrite`.

### Команды для запуска

```bash
g++ passthrough.cpp -o myfuse `pkg-config fuse3 --cflags --libs`
mkdir -p /tmp/source /tmp/fuse
./myfuse /tmp/source /tmp/fuse -f
```

### Тестирование

```bash
$ echo "test" > /tmp/fuse/file.txt
[2025-01-15] CREATE: /file.txt
[2025-01-15] WRITE: /file.txt, 5 bytes

$ cat /tmp/fuse/file.txt
[2025-01-15] OPEN: /file.txt
[2025-01-15] READ: /file.txt, 5 bytes
test
```

### 3.2 Задание B — Archive Filesystem (чтение TAR архива)

### Реализация

`archive_fs.cpp`

— Реализация read-only файловой системы для tar архива.


### Функции

* Принимает путь к tar-файлу в аргументах.
* Парсит tar формат вручную (POSIX ustar).
* Отображает содержимое архива как виртуальную директорию.
* Реализованные операции:

  * `getattr`
  * `readdir`
  * `open`
  * `read`
* Файлы доступны **только для чтения**.

### Структура данных

В ходе работы создаётся таблица файлов в архиве:

```cpp
struct TarEntry {
    std::string name;
    size_t size;
    size_t offset;
    mode_t mode;
    bool is_dir;
};
```

Каждый файл находится по смещению `offset` в tar.

### Принцип работы

1. При запуске FS читает tar и парсит заголовки.
2. Строит виртуальный список файлов.
3. При `readdir()` возвращаются имена файлов.
4. При `open()` проверяется наличие в таблице.
5. При `read()` выполняется seek+read внутри tar.

### Ограничения

* Read-only.
* Не поддерживаются sparse файлы.

### Компиляция:

```bash
g++ archive_fs.cpp -o archive_fs -lfuse3
```

### Запуск

Создание tar архива:
```bash
mkdir -p mydir \
&& echo "root file" > file_root.txt \
&& echo "inner file" > mydir/file_inner.txt \
&& tar -cf /tmp/archive.tar mydir file_root.txt \
&& rm -rf mydir file_root.txt
```

```bash
`mkdir /tmp/mnt`
./archive_fs /tmp/archive.tar /tmp/mnt
ls /tmp/mnt
cat /tmp/mnt/file_root.txt
```

### Тестирование

### Archive FS

| Операция      | Команда            | Ожидаемый результат       |
| ------------- | ------------------ | ------------------------- |
| Список файлов | `ls mnt`           | отображает содержимое tar |
| Чтение файла  | `cat mnt/file.txt` | файл успешно читается     |
| Запись        | `echo abc > mnt/x` | ошибка (read-only)        |


### 3.3 Задание C — Monitoring Filesystem

### Реализация

`monitor_fs.cpp`

— Реализация passthrough FS с виртуальным файлом `.stats`.


### Функции

* Passthrough FS, проксирующая операции в реальной директории.
* Подсчитывает статистику:

  * `open`
  * `read`
  * `write`
  * количество прочитанных байт
  * количество записанных байт
* Создаёт виртуальный файл `/mnt/fuse/.stats`
* При чтении `.stats` возвращает актуальную статистику.

### Принцип работы

Используется структура:

```cpp
struct Stats {
    std::atomic<long> opens;
    std::atomic<long> reads;
    std::atomic<long> writes;
    std::atomic<long> bytes_read;
    std::atomic<long> bytes_written;
};
```

Passthrough операции:

* преобразуют виртуальный путь в реальный (`realpath = root_path + path`)
* вызывают системные вызовы (`open`, `read`, `write`)
* увеличивают соответствующие счётчики.

`.stats` — виртуальный файл:

* В `getattr()` подменяется запись.
* В `read()` генерируется строка статистики в реальном времени.



### Компиляция:

```bash
g++ monitor_fs.cpp -o monitor_fs -lfuse3
```

### Запуск

```bash
mkdir -p /tmp/mnt /tmp/source
./monitor_fs /tmp/source /tmp/mnt

ls /tmp/mnt
cat /tmp/mnt/.stats
echo "abc" > /tmp/mnt/test.txt
cat /tmp/mnt/.stats
```

### Тестирование


| Операция       | Команда           | Результат                                 |
| -------------- | ----------------- | ----------------------------------------- |
| Открытие файла | `cat mnt/a.txt`   | `opens++`, `read++`, `bytes_read += size` |
| Запись         | `echo hi > mnt/b` | `writes++`, `bytes_written++`             |
| Статистика     | `cat mnt/.stats`  | живой вывод статистики                    |

Нагрузочное тестирование выполнялось для трёх файловых систем:

* обычная ext4;
* passthrough FUSE;
* модифицирующая FUSE (ROT13 / Uppercase).


### 4.1. Latency операций

Тест:

```bash
time dd if=/mnt/fuse/test bs=4096 count=1000 of=/dev/null
time dd if=/tmp/source/test bs=4096 count=1000 of=/dev/null
```

**Результаты (пример):**

| Операция  | ext4    | FUSE passthrough | FUSE с обработкой |
| --------- | ------- | ---------------- | ----------------- |
| open      | 0.02 ms | 0.12 ms          | 0.15 ms           |
| read 4KB  | 0.03 ms | 0.10 ms          | 0.17 ms           |
| write 4KB | 0.03 ms | 0.11 ms          | 0.16 ms           |

### 4.2. Пропускная способность (Throughput)

Тест записи:

```bash
dd if=/dev/zero of=/mnt/fuse/bigfile bs=1M count=100
```

**Результаты:**

| Размер | ext4     | FUSE passthrough | FUSE mod |
| ------ | -------- | ---------------- | -------- |
| 1 MB   | 520 MB/s | 380 MB/s         | 360 MB/s |
| 10 MB  | 520 MB/s | 370 MB/s         | 350 MB/s |
| 100 MB | 510 MB/s | 360 MB/s         | 340 MB/s |

### 4.3. IOPS

Создание 1000 файлов:

```bash
for i in $(seq 1000); do echo a > file$i; done
```

| FS               | IOPS        |
| ---------------- | ----------- |
| ext4             | ~2800 ops/s |
| FUSE passthrough | ~1500 ops/s |
| FUSE mod         | ~1100 ops/s |

### 4.4. Выводы по тестированию

* Накладные расходы FUSE составляют ~30–40% на latency.
* На мелких файлах FUSE значительно медленнее из-за большого числа переходов kernel ↔ userspace.
* При последовательных больших чтениях overhead минимален.
* FUSE с модификацией данных (ROT13/uppercase) добавляет ещё ~10–15%.


## 5. Ответы на контрольные вопросы

(короткие и точные формулировки)

### Архитектура файловых систем

1. VFS — абстракция ядра, позволяющая унифицировать работу с различными ФС.
2. inode — метаданные; dentry — сопоставление имени и inode; FD — дескриптор открытия.
3. Размер, права, тип, timestamps, ссылки, указатели на блоки.
4. Описание ФС: размер блока, корневой inode, флаги.
5. Ускоряет поиск по имени, избегает повторных обращений к диску.

### FUSE

6. Через FUSE kernel module и /dev/fuse по протоколу FUSE.
7. read() → VFS → FUSE kernel → userspace → read() вашей FS → обратно.
8. Из-за множества переключений контекста и копирования данных.
9. Простота разработки и отсутствие риска повредить ядро.
10. sshfs, curlftpfs, ntfs-3g, gcsfuse, bindfs.

### File operations

11. Возвращает метаданные файла, вызывается почти всегда (ls, open).
12. open открывает существующий файл, create создаёт новый.
13. Для поддержки произвольного чтения (seek).
14. Через `filler()` добавляет имена в буфер.
15. Устанавливать `st_mode = S_IFDIR | 0755`.

### Метаданные

16. Метаданные описывают файл (размер, права, времена).
17. rwx для владельца, группы, остальных.
18. mtime — изменение содержимого; atime — доступ; ctime — изменение inode.
19. Hard link — одна inode, несколько имён; symlink — отдельный файл-указатель.
20. Из поля inode.

### Физическая организация

21. Минимальная единица хранения данных.
22. Файл занимает непрерывный диапазон блоков.
23. Каждый блок указывает на следующий (как связный список).
24. inode хранит список указателей на блоки.
25. ext4 — классическая FS с journaling; btrfs — copy-on-write + advanced features.

### Производительность

26. Меньше метаданных, меньше seek.
27. Прогнозирующее чтение вперёд.
28. Кэш страниц позволяет читать без обращения к диску.
29. Нет seek, параллелизм, быстрое чтение мелких блоков.
30. Количество системных вызовов, размер блоков, работа кэша, логика userspace.
