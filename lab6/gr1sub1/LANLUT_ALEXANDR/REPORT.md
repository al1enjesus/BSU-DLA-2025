## 2. Теоретическая часть

### 2.1. Virtual File System (VFS)

VFS - это абстрактный слой в ядре Linux, который предоставляет единый интерфейс для работы с различными файловыми системами. VFS обеспечивает универсальный API для всех типов файловых систем (ext4, btrfs, NFS, FUSE и т.д.), позволяя приложениям использовать одни и те же системные вызовы независимо от типа файловой системы.

**Ключевые структуры VFS:**

- **superblock** - описывает файловую систему в целом: размер блока, количество свободных блоков, root inode, магическое число ФС
- **inode** - метаданные файла: размер, права доступа (mode), владелец (uid/gid), временные метки (mtime/atime/ctime), тип файла, ссылки на блоки данных
- **dentry** (directory entry) - элемент кеша имён каталогов, связывает имя файла с inode, ускоряет поиск файлов
- **file** - структура открытого файла: позиция чтения/записи (offset), флаги открытия (O_RDONLY, O_WRONLY), указатель на inode

### 2.2. Архитектура FUSE

FUSE позволяет создавать файловые системы в пользовательском пространстве без необходимости писать код для ядра. Это значительно упрощает разработку и отладку.

**Поток выполнения операций:**

```
Приложение (cat, ls)
       ↓
   syscall (open, read)
       ↓
   VFS (ядро Linux)
       ↓
  FUSE kernel module
       ↓
  /dev/fuse (протокол FUSE)
       ↓
  libfuse (userspace)
       ↓
  Ваша программа (passthrough, rot13_fs, uppercase_fs)
       ↓
  Реальная ФС (ext4, tmpfs)
```

**Преимущества FUSE:**

- **Безопасность разработки** - ошибки в коде не приводят к kernel panic
- **Доступ к библиотекам userspace** - можно использовать libcurl, libarchive, OpenSSL и др.
- **Простота отладки** - можно использовать gdb, valgrind, strace
- **Кроссплатформенность** - один и тот же код работает на Linux, macOS, FreeBSD

**Недостатки FUSE:**

- **Overhead на context switch** - переключение между kernel и userspace добавляет 20-40% задержки
- **Копирование данных** - данные копируются между kernel space и userspace
- **Производительность** - медленнее нативных файловых систем на 15-30%

### 2.3. Основные операции FUSE

В рамках работы реализованы следующие операции:

- **getattr** - получение метаданных файла (размер, права, временные метки)
- **readdir** - чтение содержимого директории
- **open** - открытие существующего файла
- **read** - чтение данных из файла
- **write** - запись данных в файл
- **create** - создание нового файла
- **unlink** - удаление файла
- **mkdir** - создание директории
- **rmdir** - удаление директории
- **chmod** - изменение прав доступа
- **chown** - изменение владельца
- **truncate** - изменение размера файла
- **utimens** - изменение временных меток

### 3.2. Задание B - ROT13 Encryption Filesystem

#### Описание

Реализована FUSE FS с простым ROT13 шифрованием. Файлы на диске хранятся в зашифрованном виде, но через FUSE монтирование читаются в расшифрованном виде.

ROT13 - это шифр подстановки, который заменяет каждую букву буквой, отстоящей от неё на 13 позиций в алфавите:
- A → N, B → O, ..., M → Z, N → A, ..., Z → M
- a → n, b → o, ..., m → z, n → a, ..., z → m

#### Реализация

Ключевые функции:

1. **rot13_char()** - преобразует один символ:
   ```cpp
   'H' → 'U', 'e' → 'r', 'l' → 'y', 'o' → 'b'
   ```

2. **rot13_buffer()** - применяет ROT13 к буферу данных

3. **rot13_read()** - читает зашифрованные данные с диска и расшифровывает их

4. **rot13_write()** - шифрует данные и записывает на диск

#### Команды для запуска

```bash
cd src/
make
mkdir -p /tmp/source /tmp/fuse

```

#### Тестирование

## 5. Ответы на контрольные вопросы

### Архитектура файловых систем

**1. Что такое VFS (Virtual File System) и зачем она нужна?**

VFS - это абстрактный слой в ядре Linux, который предоставляет единый интерфейс для всех типов файловых систем. VFS позволяет приложениям использовать одинаковые системные вызовы (open, read, write) независимо от того, какая ФС используется (ext4, NFS, FUSE). Это обеспечивает прозрачность и совместимость.

**2. Объясните разницу между inode, dentry и file descriptor.**

- **inode** - структура данных, хранящая метаданные файла (размер, права, владелец, временные метки, указатели на блоки данных). Идентифицируется уникальным номером inode.
- **dentry** (directory entry) - элемент кеша каталогов, связывающий имя файла с его inode. Ускоряет поиск файлов по имени.
- **file descriptor** - целое число, идентифицирующее открытый файл в процессе. Указывает на структуру file в ядре, содержащую позицию чтения/записи и флаги.

**3. Что хранится в структуре `struct inode`?**

- Тип файла (обычный файл, директория, symbolic link, device)
- Права доступа (mode: rwxrwxrwx)
- Владелец (uid) и группа (gid)
- Размер файла в байтах
- Временные метки: atime (время доступа), mtime (время модификации), ctime (время изменения метаданных)
- Количество hard links на файл
- Указатели на блоки данных (прямые, косвенные, двойной косвенности)

**4. Что такое superblock и какую информацию он содержит?**

Superblock - это структура данных, описывающая файловую систему в целом:
- Магическое число (идентификатор типа ФС)
- Размер блока (обычно 4KB)
- Общее количество блоков и inode
- Количество свободных блоков и inode
- Указатель на root inode (корневую директорию)
- Флаги состояния ФС (чистая/грязная, read-only)
- Дата последнего монтирования

**5. Как работает кеш dentry и зачем он нужен?**

Кеш dentry хранит соответствия "имя файла → inode" в оперативной памяти. При обращении к файлу `/home/user/file.txt` ядро проходит путь: root → home → user → file.txt. Без кеша пришлось бы каждый раз читать inode директорий с диска. Кеш dentry ускоряет повторные обращения к одним и тем же файлам, храня уже разрешенные пути.

### FUSE

**6. Как FUSE взаимодействует с ядром Linux?**

FUSE использует kernel module `/dev/fuse` для коммуникации:
1. VFS получает системный вызов (например, read)
2. VFS передает запрос FUSE kernel module
3. Kernel module записывает запрос в очередь `/dev/fuse`
4. Библиотека libfuse в userspace читает запрос из `/dev/fuse`
5. libfuse вызывает соответствующую функцию программы (например, `myfs_read()`)
6. Результат передается обратно через `/dev/fuse` → kernel → VFS → приложение

**7. Опишите путь системного вызова `read()` в FUSE FS.**

```
1. cat вызывает read(fd, buf, size)
2. Системный вызов попадает в ядро
3. VFS определяет, что fd относится к FUSE FS
4. VFS вызывает fuse_read() из kernel module
5. FUSE kernel формирует FUSE request и помещает в очередь
6. libfuse читает request из /dev/fuse
7. libfuse вызывает зарегистрированную функцию myfs_read()
8. myfs_read() выполняет реальное чтение (например, из файла)
9. Данные возвращаются через libfuse → /dev/fuse
10. FUSE kernel копирует данные в буфер приложения
11. cat получает данные
```

**8. Почему FUSE работает медленнее нативных kernel FS?**

Основные причины:
1. **Context switch** - переключение между kernel space и userspace (дорогая операция)
2. **Копирование данных** - данные копируются дважды: disk → kernel → userspace → kernel → application
3. **Overhead протокола** - дополнительные структуры данных для FUSE protocol
4. **Отсутствие оптимизаций ядра** - kernel FS могут использовать прямой доступ к DMA, zero-copy и т.д.

**9. Какие преимущества дает разработка FS в userspace?**

- **Безопасность** - ошибки не приводят к kernel panic
- **Простота разработки** - можно использовать обычные библиотеки (libcurl, OpenSSL)
- **Отладка** - доступны gdb, valgrind, strace
- **Портируемость** - один код работает на разных ОС
- **Быстрая разработка** - не нужно знать kernel API
- **Динамическая загрузка** - можно обновлять без перезагрузки системы

**10. Приведите примеры популярных FUSE файловых систем.**

- **sshfs** - монтирование удаленной директории через SSH
- **Google Cloud Storage FUSE (gcsfuse)** - доступ к Google Cloud Storage как к локальной ФС
- **NTFS-3G** - поддержка NTFS на Linux
- **EncFS** - шифрование файловой системы
- **S3FS** - монтирование Amazon S3 bucket
- **SSHFS** - удаленный доступ к файлам через SSH
- **ZipFS** - чтение ZIP архивов как директорий

### File operations

**11. Что делает операция `getattr()` и когда она вызывается?**

`getattr()` возвращает метаданные файла (эквивалент системного вызова `stat()`). Заполняет структуру `struct stat` полями: размер файла, права доступа, владелец, временные метки, тип файла.

Вызывается при:
- `ls -l` (для отображения размера, прав)
- `stat file.txt`
- Открытии файла (проверка существования)
- До чтения/записи (проверка прав)

**12. В чем разница между `open()` и `create()`?**

- **open()** - открывает существующий файл, возвращает file descriptor. Если файл не существует и передан флаг `O_CREAT`, создает файл.
- **create()** - всегда создает новый файл с указанными правами. Эквивалентна `open()` с флагами `O_CREAT | O_WRONLY | O_TRUNC`.

В FUSE:
- `create()` вызывается при создании нового файла
- `open()` вызывается при открытии существующего файла

**13. Почему `read()` принимает параметр `offset`?**

Параметр `offset` указывает позицию в файле, с которой нужно начать чтение. Это позволяет:
- Читать файл не последовательно (random access)
- Нескольким процессам читать разные части файла одновременно
- Избегать хранения позиции в file descriptor (stateless операция)
- Поддерживать `pread()` - атомарное чтение с указанной позиции без изменения file offset

**14. Как `readdir()` возвращает список файлов?**

`readdir()` получает указатель на функцию `filler`, которую нужно вызывать для каждого файла в директории:

```cpp
int readdir(const char *path, void *buf, fuse_fill_dir_t filler, ...) {
    DIR *dp = opendir(path);
    struct dirent *de;
    while ((de = readdir(dp)) != NULL) {
        filler(buf, de->d_name, &stat, 0);  // добавляем файл
    }
    closedir(dp);
    return 0;
}
```

`filler()` добавляет информацию о файле в буфер, который возвращается приложению.

**15. Что должна возвращать `getattr()` для директории?**

Для директории `getattr()` заполняет `struct stat`:
- `st_mode = S_IFDIR | 0755` - тип: директория, права: rwxr-xr-x
- `st_nlink = 2 + количество_поддиректорий` - количество hard links
- `st_size` - обычно 4096 (размер блока)
- `st_uid`, `st_gid` - владелец
- Временные метки (mtime, atime, ctime)

### Метаданные и атрибуты

**16. Что такое атрибуты файла? Приведите примеры.**

Атрибуты файла - это метаданные, описывающие свойства файла:
- **Права доступа** (mode): rwxr-xr-x (0755)
- **Владелец** (uid, gid): user:group
- **Размер** (size): 1024 bytes
- **Временные метки**: mtime, atime, ctime
- **Тип файла**: обычный файл, директория, symbolic link
- **Количество hard links** (nlink)
- **Расширенные атрибуты** (xattr): метки безопасности, ACL

**17. Что означают биты прав доступа (rwxrwxrwx)?**

Права доступа состоят из 9 бит, разделенных на 3 группы:
- **rwx** (биты 6-8) - права владельца (user)
- **rwx** (биты 3-5) - права группы (group)
- **rwx** (биты 0-2) - права остальных (others)

Где:
- **r (4)** - read (чтение файла, список директории)
- **w (2)** - write (запись в файл, создание/удаление в директории)
- **x (1)** - execute (выполнение файла, вход в директорию)

Пример: `rwxr-xr--` = 754 = владелец может все, группа может читать и выполнять, остальные только читать.

**18. Объясните разницу между mtime, atime и ctime.**

- **mtime** (modification time) - время последнего изменения содержимого файла (запись данных)
- **atime** (access time) - время последнего доступа к файлу (чтение)
- **ctime** (change time) - время последнего изменения метаданных файла (chmod, chown, переименование)

**19. Что такое hard link и как он отличается от symbolic link?**

**Hard link:**
- Еще одно имя для того же inode
- Несколько имен указывают на одни и те же данные
- Удаление одного имени не удаляет файл, пока есть другие hard links
- Не может указывать на директорию (во избежание циклов)
- Работает только в пределах одной файловой системы

**Symbolic link (symlink):**
- Специальный файл, содержащий путь к другому файлу
- Имеет свой собственный inode
- Может указывать на директорию
- Может указывать на файл в другой файловой системе
- Если целевой файл удален, symlink становится "битым"

**20. Как FS определяет размер файла?**

Размер файла хранится в поле `st_size` структуры inode. Для обычных файлов это количество байт данных. Для директорий - размер структуры каталога (обычно кратно размеру блока).

ФС обновляет размер при:
- Записи данных (увеличение)
- Усечении файла `truncate()` (уменьшение)
- Добавлении данных в конец файла

### Физическая организация

**21. Что такое блок в файловой системе?**

Блок - это минимальная единица хранения данных на диске. Обычные размеры:
- **4 KB (4096 bytes)** - стандарт для большинства ФС
- **8 KB** - некоторые серверные ФС
- **512 bytes** - старые ФС

Файловая система выделяет пространство блоками целиком, даже если файл меньше блока. Например, файл размером 100 bytes займет целый блок 4 KB.

**22. Объясните принцип непрерывного размещения файлов (contiguous allocation).**

Файл хранится в последовательных блоках на диске без разрывов.

**Преимущества:**
- Быстрое последовательное чтение (минимум seek операций)
- Простая реализация (нужно знать только начальный блок и длину)

**Недостатки:**
- Фрагментация диска (сложно найти непрерывный блок нужного размера)
- Невозможно расширить файл, если следующие блоки заняты
- Требуется дефрагментация

Используется в CD-ROM, некоторых embedded системах.

**23. Как работает организация через связанный список блоков (linked allocation)?**

Каждый блок содержит указатель на следующий блок файла. Последний блок указывает на NULL.

**Преимущества:**
- Нет внешней фрагментации
- Файлы могут легко расширяться

**Недостатки:**
- Медленный random access (нужно пройти весь список)
- Потеря одного блока ломает весь файл
- Накладные расходы на хранение указателей

Используется в FAT (File Allocation Table).

**24. Что такое индексный узел (inode-based allocation)?**

Каждый файл имеет inode - структуру, содержащую указатели на блоки данных:
- **Прямые указатели** (12-15 штук) - указывают прямо на блоки данных
- **Косвенный указатель** - указывает на блок с указателями на данные
- **Двойной косвенный указатель** - указывает на блок с указателями на блоки с указателями
- **Тройной косвенный указатель** - еще один уровень косвенности

**Преимущества:**
- Быстрый random access
- Эффективное использование для маленьких и больших файлов
- Поддержка разреженных файлов (sparse files)

Используется в ext2/3/4, UFS.

**25. Сравните ext4 и btrfs по структуре хранения данных.**

**ext4:**
- Основана на inode
- Фиксированное количество inode при создании ФС
- Журналирование (journaling) для метаданных
- Экстенты (extents) - непрерывные области блоков вместо отдельных указателей
- Максимальный размер файла: 16 TB
- Нет встроенных snapshots

**btrfs:**
- Copy-on-Write (CoW) - данные никогда не перезаписываются на месте
- B-tree структура для индексации
- Динамическое выделение inode
- Встроенные snapshots и cloning
- Checksums для всех данных и метаданных
- RAID поддержка на уровне ФС
- Сжатие данных "на лету"
- Максимальный размер файла: 16 EB (exabytes)

### Производительность и оптимизация

**26. Почему большие файлы читаются быстрее, чем много мелких?**

Причины:
1. **Overhead на системные вызовы** - каждый `open()`, `read()`, `close()` требует context switch. Для множества мелких файлов overhead накапливается.
2. **Меньше seek операций** - большой файл обычно расположен непрерывно, меньше перемещений головки HDD.
3. **Лучше работает read-ahead** - ядро предсказывает последовательное чтение и загружает данные заранее.
4. **Меньше обращений к метаданным** - для каждого файла нужно читать inode, для одного большого файла - один inode.

**27. Что такое read-ahead и как он улучшает производительность?**

Read-ahead - это механизм предварительной загрузки данных в page cache. Когда ядро обнаруживает последовательное чтение файла, оно автоматически загружает следующие блоки в память до того, как они запрошены.

**Преимущества:**
- Скрывает latency диска
- Данные уже в памяти к моменту запроса
- Эффективно использует пропускную способность диска

Например, при чтении блока 10, ядро может загрузить блоки 11-15 заранее.

**28. Как page cache ускоряет доступ к файлам?**

Page cache - это область оперативной памяти, где кешируются страницы файлов.

**Механизм:**
1. При первом чтении файла данные загружаются с диска в page cache
2. Повторные чтения берут данные из RAM (в тысячи раз быстрее)
3. При записи данные сначала попадают в page cache, затем асинхронно сбрасываются на диск
4. Ядро использует LRU (Least Recently Used) для вытеснения старых страниц

**Преимущества:**
- Чтение из RAM вместо диска (latency: 100 нс vs 10 мс)
- Объединение множества мелких записей в одну большую
- Снижение количества I/O операций

**29. Почему запись на SSD быстрее, чем на HDD?**

**SSD (Solid State Drive):**
- Нет механических частей (нет задержек на перемещение головки)
- Случайный доступ ~0.1 мс
- Параллельный доступ к множеству чипов памяти
- Высокий IOPS (100,000+ операций/сек)

**HDD (Hard Disk Drive):**
- Механическое перемещение головки (seek time ~5-10 мс)
- Вращение диска (rotational latency ~4 мс)
- Последовательный доступ намного быстрее случайного
- Низкий IOPS (~100-200 операций/сек)

Для случайных операций SSD быстрее в 100-1000 раз.

**30. Какие параметры влияют на производительность FUSE FS?**

1. **Размер буфера** - больший буфер снижает количество системных вызовов
2. **Кеширование** - использование page cache, dentry cache
3. **Многопоточность** - параллельная обработка запросов (опция `multi-threaded`)
4. **Direct I/O** - отключение буферизации для некоторых сценариев
5. **Оптимизация read-ahead** - настройка размера предварительного чтения
6. **Батчинг операций** - объединение множества мелких операций
7. **Асинхронные операции** - неблокирующий I/O
8. **Опции монтирования:**
   - `big_writes` - разрешить большие записи (>4KB)
   - `max_write=N` - максимальный размер записи
   - `async_read` - асинхронное чтение

## 6. Выводы

В ходе лабораторной работы были успешно реализованы три типа FUSE файловых систем:

1. **Passthrough FS** - базовая реализация, демонстрирующая принципы работы FUSE
2. **ROT13 Encryption FS** - файловая система с прозрачным шифрованием на лету
3. **Uppercase FS** - файловая система с трансформацией данных при чтении

**Интересные находки:**

- FUSE обеспечивает удобный способ создания файловых систем в userspace без необходимости программирования на уровне ядра
- Overhead FUSE составляет 30-40% для единичных операций, но приемлем для работы с большими файлами
- Логирование операций помогло понять, как простые команды bash вызывают целые цепочки файловых операций
- Модификация данных "на лету" (ROT13, uppercase) возможна прозрачно для приложений

**Сложности:**

- Понимание взаимодействия между VFS, FUSE kernel module и userspace программой
- Правильная обработка ошибок и возврат кодов errno
- Управление memory allocation при работе с буферами (особенно в rot13_fs)
