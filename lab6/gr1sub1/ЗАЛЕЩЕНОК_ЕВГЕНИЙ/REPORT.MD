## 2. Теоретическая часть

### Архитектура VFS
**Virtual File System (VFS)** — это слой абстракции в ядре Linux, который позволяет приложениям работать с различными файловыми системами (ext4, btrfs, NTFS, FUSE) через единый API (`open`, `read`, `write`).

**Ключевые структуры:**
*   **Inode (Index Node):** Описывает метаданные файла (размер, права, владелец, временные метки). Не содержит имени файла.
*   **Dentry (Directory Entry):** Связывает имя файла с его inode. Образует дерево директорий. Кешируется в памяти (dcache) для ускорения поиска.
*   **Superblock:** Описывает параметры всей файловой системы (размер блока, статус монтирования).
*   **File:** Структура, представляющая открытый файл в процессе (текущая позиция курсора, режим доступа).

### FUSE (Filesystem in Userspace)
FUSE позволяет создавать драйверы файловых систем как обычные процессы пользователя.
**Поток данных:**
1.  Приложение вызывает `read()`.
2.  Ядро (VFS) перенаправляет запрос в модуль ядра FUSE.
3.  Модуль пишет запрос в устройство `/dev/fuse`.
4.  Библиотека `libfuse` в userspace читает запрос и вызывает соответствующую функцию в моей программе (`do_read`).
5.  Программа выполняет операцию и возвращает результат обратно по той же цепочке.

## 3. Ход выполнения работы

В рамках работы были реализованы две программы:

### Реализация `myfuse` (Задания A и C)

Реализована "сквозная" (passthrough) файловая система, которая зеркалирует указанную директорию.

**Ключевые функции:**
*   `do_getattr`: Преобразует путь FUSE в реальный путь и вызывает `lstat`. Перехватывает путь `/.stats` для выдачи информации о виртуальном файле.
*   `do_read` / `do_write`: Вызывают системные `pread`/`pwrite`. Ведут подсчет количества операций и переданных байт в глобальной структуре `fs_stats`.
*   `do_readdir`: Читает содержимое реальной директории и добавляет в список виртуальный файл `.stats`.

**Система мониторинга (Задание C):**
При чтении файла `/.stats` содержимое генерируется динамически через `sprintf`, отображая текущие счетчики операций чтения, записи и открытий файлов.

### Реализация `archivefs` (Задание B)

В качестве дополнительного задания реализована `read-only` файловая система для просмотра TAR-архивов.
*   При запуске программа парсит заголовки TAR (блоки по 512 байт) и строит связанный список файлов в памяти.
*   `do_readdir` возвращает список файлов из архива.
*   `do_read` находит смещение (offset) данных внутри `.tar` файла и читает их, эмулируя работу с обычным файлом.

*   На больших файлах падение скорости составляет примерно **4 раза** (из-за копирования данных между kernel/user space).
*   На мелких операциях (создание файлов) замедление достигает **10-12 раз**, так как каждая операция требует переключения контекста процесса (Context Switch), что является дорогой операцией для процессора.

## 5. Ответы на контрольные вопросы

### Архитектура файловых систем
1.  **Что такое VFS?** Это абстрактный слой ядра, предоставляющий единый интерфейс системных вызовов для всех типов ФС.
2.  **Inode vs Dentry vs File descriptor:** `Inode` — метаданные файла; `Dentry` — имя файла и ссылка на inode; `File descriptor` — номер открытого файла в таблице процесса.
3.  **Структура `struct inode`:** Содержит права доступа, ID владельца/группы, размер, временные метки (atime, mtime, ctime), счетчик ссылок, указатели на блоки данных.
4.  **Superblock:** Содержит глобальную информацию о ФС: размер блока, общее число блоков, UUID, статус (ro/rw).
5.  **Dentry cache:** Кэш в оперативной памяти, хранящий связи "имя файла" -> "inode". Нужен для ускорения поиска путей, чтобы не читать диск каждый раз.

### FUSE
6.  **Взаимодействие с ядром:** Через символьное устройство `/dev/fuse`. Ядро посылает туда запросы, userspace-демон их читает.
7.  **Путь `read()` в FUSE:** App -> Syscall -> VFS -> FUSE Kernel Module -> `/dev/fuse` -> libfuse -> User Code (`do_read`) -> Syscall (`pread`) -> Disk -> возврат данных обратно.
8.  **Почему FUSE медленнее?** Из-за накладных расходов на переключение контекста (Kernel <-> User) и лишнего копирования буферов данных.
9.  **Преимущества Userspace FS:** Безопасность (сбой не роняет ОС), легкость разработки и отладки, доступ к user-level библиотекам (сеть, сжатие).
10. **Примеры FUSE:** `sshfs`, `ntfs-3g`, `glusterfs`, `googledrive-ocamlfuse`.

### File operations
11. **`getattr()`:** Аналог системного вызова `stat`. Вызывается для получения метаданных (размер, права). Вызывается почти при любой операции (ls, cp).
12. **`open()` vs `create()`:** `open` открывает существующий файл. `create` создает новый. В FUSE `create` обычно реализуется как атомарная операция создания + открытия.
13. **Параметр `offset` в `read()`:** Указывает, с какого байта читать. FUSE не хранит состояние курсора ("seek pointer") внутри драйвера, это ответственность ядра.
14. **`readdir()`:** Возвращает список файлов, вызывая функцию-заполнитель `filler` для каждого имени файла в директории.
15. **`getattr()` для директории:** Должен возвращать `st_mode` с флагом `S_IFDIR` и права доступа (обычно 0755).

### Метаданные и атрибуты
16. **Атрибуты файла:** Размер, права (mode), владелец (uid), группа (gid), времена (atime, mtime, ctime).
17. **rwxrwxrwx:** 9 бит прав доступа. 3 группы (User, Group, Others). r=Read(4), w=Write(2), x=Execute(1).
18. **mtime/atime/ctime:** `mtime` (Modification) — изменение контента; `atime` (Access) — последнее чтение; `ctime` (Change) — изменение метаданных.
19. **Hard link vs Symlink:** Хардлинк — это еще одно имя для того же inode. Симлинк — отдельный файл, содержащий путь к цели. Хардлинк не работает между разными ФС.
20. **Размер файла:** Определяется полем `st_size` в inode.

### Физическая организация
21. **Блок:** Минимальная адресуемая единица хранения на диске (обычно 4 КБ).
22. **Contiguous allocation:** Файл занимает непрерывную последовательность блоков. Плюсы: скорость. Минусы: фрагментация, сложно менять размер.
23. **Linked allocation:** Блоки разбросаны, каждый хранит ссылку на следующий. Плюсы: нет внешней фрагментации. Минусы: медленный произвольный доступ.
24. **Inode-based allocation:** Инод хранит массив адресов блоков. Используется в Unix (ext4). Быстрый доступ и гибкость.
25. **ext4 vs btrfs:** ext4 — классическая журнальная ФС. btrfs — Copy-on-Write (COW) система с поддержкой снапшотов, пулов и чексумм данных.

### Производительность
26. **Большие файлы vs мелкие:** Большие читать быстрее, так как меньше операций поиска (seek) и меньше накладных расходов на открытие/закрытие.
27. **Read-ahead:** Технология, при которой ОС подгружает в кэш блоки, следующие за текущим читаемым, предугадывая последовательное чтение.
28. **Page cache:** Кэш страниц в RAM. Позволяет повторно читать данные из памяти, не обращаясь к медленному диску.
29. **SSD vs HDD:** SSD не имеет движущихся частей, поэтому время поиска (seek time) почти нулевое, что критично для мелких файлов.
30. **Параметры FUSE:** Размер буфера, опции `direct_io`, `kernel_cache`, `big_writes`, `auto_cache` влияют на производительность.

## 6. Использование Искусственного Интеллекта

ИИ использовался для создания "скелета" приложения (`fuse_operations`), что позволило сосредоточиться на реализации бизнес-логики (сбор статистики и парсинг архива), а не на рутинном написании заголовков.

    *   **Виртуальные файлы:** Был сгенерирован пример реализации динамического буфера для файла `/.stats` с использованием `sprintf`, что упростило выполнение задания по мониторингу.
