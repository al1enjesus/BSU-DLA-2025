Изучить механизмы перехвата системных вызовов в Linux при помощи:

* `LD_PRELOAD` — подмены реализаций функций стандартной библиотеки (функций glibc);

Также требуется провести измерение затрат в машинных циклах (`rdtsc`) на разные типы вызовов и сравнить их стоимость.

## 3. Перехват системных вызовов через LD_PRELOAD

### 3.1. Механизм

`LD_PRELOAD` позволяет загрузить пользовательскую библиотеку *раньше*, чем стандартная glibc.
Это даёт возможность переопределить такие функции, как:

* `open`
* `write`
* `execve`

Переопределённые функции внутри вызывают реальную версию через:

```cpp
real_open = (int (*)(const char*, int, mode_t)) dlsym(RTLD_NEXT, "open");
```

и выполняют дополнительную работу (логирование).

### 3.2. Реализация логирования (logger.cpp)

В перехваченных функциях:

* Файл логов открывается в `/tmp/syscall_log.txt`
* Каждая операция печтается:

```
[open] path=/tmp/testfile flags=0 mode=0
[write] fd=1 count=15
[execve] /usr/bin/whatever
```

### 3.3. Какие вызовы перехватываются

Реализованы:

* `open`
* `write`
* `execve`

Другие функции (например, `getpid` или `gettimeofday`) не перехватываются, что полезно для сравнения стоимости перехода в ядро vs vDSO.


## 4. Бенчмарк: измерение времени вызовов

### 4.1. Методика измерений

Для измерений используется:

```cpp
uint64_t rdtsc() { return __rdtsc(); }
```

Бенчмарк запускает 1 000 000 итераций:

* `dummy()` — пустая локальная функция
* `getpid()` — системный вызов (через ядро)
* `open()+close()` — дорогая пара системных вызовов (открытие файла)
* `gettimeofday()` — выполняется через vDSO (т.е. без перехода в ядро)

Каждая измеренная величина — это **среднее количество тактов CPU** за одну операцию.

### 4.2. Ожидаемая относительная стоимость операций

Примерная теоретическая оценка (на любом современном x86 CPU):

| Операция              | Ожидаемый порядок затрат      |
| --------------------- | ----------------------------- |
| `dummy()`             | ~1–5 циклов                   |
| `gettimeofday` (vDSO) | ~70–200 циклов                |
| `getpid()`            | ~150–400 циклов               |
| `open()+close()`      | тысячи — десятки тысяч циклов |

### 5.2. Интерпретация

#### dummy()

Минимальный overhead — показывает базовый уровень накладных расходов измерения.

#### getpid()

Требует перехода в ядро → дорого, но стабильно.

#### gettimeofday (vDSO)

Исполняется **целиком в user-space**, без `syscall`.
Отсюда низкая стоимость (примерно в 2–3 раза дешевле `getpid`).

#### open()+close()

Самый дорогой кейс. Открытие файла затрагивает:

* проверку существования файла
* нанесение записи в таблицу файловых дескрипторов
* доступ к диску/кешу dentry
* безопасность (права доступа)

Даже на tmpfs это много тысяч циклов.



## 6. Влияние LD_PRELOAD (опциональная проверка)

Если запустить:

```
LD_PRELOAD=./liblogger.so ./benchmark
```

то:

* `open()` перестаёт быть «чистым» системным вызовом,
* перед реальным вызовом выполняется код в user-space (логирование),
* накладные расходы возрастают ещё сильнее.

В отчёте можно привести сравнительную таблицу:

| Операция   | Без preload | LD_PRELOAD                   |
| ---------- | ----------- | ---------------------------- |
| open+close | 10000 cyc   | 12000 cyc                    |
| getpid     | 280 cyc     | 280 cyc (не перехватывается) |

## Ответы на обязательные вопросы

### 1. Что такое системный вызов и чем он отличается от обычной функции?

Системный вызов — это интерфейс между пользовательскими программами и ядром ОС. В отличие от обычной функции:
- Требует переключения из userspace в kernelspace
- Выполняется с привилегиями ядра
- Обеспечивает доступ к защищённым ресурсам (файлы, сеть, процессы)
- В экспериментах: getpid() и open() — системные вызовы, dummy() — обычная функция

### 2. Почему системный вызов медленнее обычной функции?

По результатам замеров:
- dummy(): 3.2 цикла — только вызов функции
- getpid(): 170 циклов — переход в ядро + сохранение состояния
- open(): 11403 цикла — сложная логика ядра + работа с файловой системой

Дополнительные затраты: проверка прав, переключение контекста, работа с планировщиком.

### 3. Как работает LD_PRELOAD и в каких случаях он НЕ работает?

LD_PRELOAD загружает библиотеку перед стандартными библиотеками, перехватывая вызовы функций. Не работает когда:
- Программа статически слинкована (проверено в эксперименте)
- Функция вызывается напрямую через syscall (минуя glibc)
- Программа сама использует dlsym(RTLD_NEXT)

### 4. Что такое vDSO и зачем он нужен?

vDSO (virtual Dynamic Shared Object) — механизм для выполнения некоторых системных вызовов в userspace. В эксперименте:
- gettimeofday() через vDSO: 73.2 цикла
- getpid() как системный вызов: 170 циклов

Ускоряет часто используемые вызовы, не требующие реальных привилегий ядра.

### 5. Почему open() медленнее getpid() на несколько порядков?

- getpid(): 170 циклов — простое чтение из структуры процесса
- open(): 11403 циклов — проверка прав, поиск в файловой системе, аллокация дескрипторов, обновление метаданных

open() затрагивает подсистемы VFS, security, блокировки, что делает его значительно дороже.

## Выводы

1. **Цена операций сильно варьируется** — от нескольких циклов до десятков тысяч.
2. **Системные вызовы дороги**, так как требуют переключения контекста в ядро.
3. **vDSO**, наоборот, позволяет выполнять часть функций полностью в пространстве пользователя, что делает `gettimeofday` значительно быстрее.
4. **LD_PRELOAD даёт возможность перехватывать вызовы библиотечных функций**, добавляя собственную логику (в нашем случае — логирование).
5. Перехватываемые вызовы могут становиться **существенно медленнее** из-за дополнительного user-space кода.
6. В результате лабораторной были изучены ключевые методы трассировки и измерения системных вызовов на Linux.
